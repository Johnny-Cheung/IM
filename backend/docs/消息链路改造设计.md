# GoIM 消息写入链路改造设计（待批准）

状态：设计评审中，暂不修改业务代码。

本文针对私聊和群聊的消息发送、实时推送、异步落库和故障恢复进行设计。目标是在不让 RabbitMQ 消费延迟阻塞实时链路的前提下，保证消息状态可同步、持久化事件不丢失，并允许后续把 relay 从主服务进程中拆成独立服务。

## 1. 已确认的设计原则

1. Redis Lua 负责发送路径中的原子业务状态变更：校验、去重、服务端消息号、服务端时间、收件箱/群发件箱、会话、未读数等。
2. RabbitMQ 只负责把持久化事件可靠交给 MySQL 消费者，不再负责写 Redis 会话状态或实时 fanout。
3. relay 第一阶段与主服务共进程，以 goroutine 运行；未来可以独立部署。
4. RabbitMQ publisher confirm 成功后，才向发送方发送 `serverAck`，并向在线接收方推送实时消息。
5. RabbitMQ 消费者按服务端消息 ID 幂等写入 MySQL；MySQL 暂时不可用时由 RabbitMQ 重试。
6. 群成员移除后必须立即不能发送群消息，Redis 成员状态不能只是尽力更新。
7. Redis 需要按持久化消息状态使用，配置 AOF/副本、禁止危险的自动淘汰，并监控积压和故障。

## 2. 目标消息链路

```text
客户端 WebSocket msg
    ↓
Go：JWT、JSON、字段、大小和消息类型校验
    ↓
Redis Lua（单次原子执行）
    ├─ 校验会话权限、禁言、黑名单
    ├─ clientMsgId 去重
    ├─ 分配 serverMsgId / groupSeq / serverTimestamp
    ├─ 写入 Redis 消息状态
    ├─ 更新会话摘要和未读数
    └─ XADD 待持久化事件到 Redis Stream
    ↓
主服务内 relay 读取 Stream
    ↓
RabbitMQ 发布并等待 publisher confirm
    ├─ 成功：XACK + XDEL，发送 serverAck，推送在线接收方
    └─ 失败/超时：保留 Stream 事件，稍后重试
    ↓
RabbitMQ 消费者
    ↓
MySQL 按 serverMsgId 幂等落库并 ACK RabbitMQ
```

这里有两个不同的“成功”概念：

- Lua 成功：消息已经写入 Redis，客户端后续同步可以看到。
- RabbitMQ confirm 成功：异步持久化事件已经可靠交给消息队列，可以给发送方确认并做实时推送。
- MySQL 落库成功：消息完成长期归档。

## 3. WebSocket 接入与 Go 层校验

客户端仍通过 `type=msg` 信封发送消息。Go 层继续负责以下不适合放入 Lua 的工作：

- JWT 身份已经由 WebSocket 接入层校验；消息发送时使用连接对应的 userID，不能信任客户端传来的 senderID。
- 解码 JSON，校验 `convType`、目标 ID、消息类型、内容长度和必填字段。
- 校验 `clientMsgId` 非空、长度合理，并限制单条消息总大小。
- 不使用客户端时间作为排序依据；客户端时间如有展示需求，可以作为普通字段保存，但消息排序使用 Redis 服务端时间。

Go 层校验失败时，不调用 Lua，不写 Redis，不产生 MQ 事件，直接返回 WebSocket `error`。

## 4. Redis Lua 原子写入

### 4.1 私聊

脚本接收发送者、接收者、clientMsgId、消息内容和消息类型，完成：

1. 检查双方好友关系。
2. 检查接收者是否把发送者加入黑名单。
3. 用 `msg_dedup:{senderId}:{clientMsgId}` 做 NX 去重，重复消息返回原有状态或明确的 duplicate 结果。
4. 用 Redis `TIME` 生成 serverTimestamp，并分配 serverMsgId。
5. 为接收者写入未读消息，为发送者写入已读副本。
6. 更新双方的会话排序和会话摘要。
7. 将完整持久化事件原子追加到 Redis Stream。

### 4.2 群聊

脚本接收群 ID、发送者、clientMsgId、消息内容和消息类型，完成：

1. 检查群成员集合和成员状态；群成员变更必须同步更新 Redis，不能只更新 MySQL 后忽略缓存失败。
2. 检查禁言状态。
3. 做消息去重。
4. 分配 serverMsgId、serverTimestamp 和群内递增的 groupSeq。
5. 将消息写入群共享发件箱。
6. 获取本次发送时的群成员快照。
7. 为每个成员更新会话摘要；除发送者外，未读数加一。
8. 将群持久化事件原子追加到 Redis Stream。
9. 返回成员快照给 Go 层，Go 层按快照向在线成员发送实时消息。

当前群上限为 500 人。单 Lua 遍历 500 人需要用压测确认耗时；如果未来要支持更大群，不能简单线性扩大脚本。

## 5. Redis 数据结构建议

当前把完整 JSON 作为 ZSet member，会导致更新会话、撤回和已读时需要扫描旧 JSON。建议改成排序索引和数据分离：

```text
inbox_order:{userId}       ZSET   msgId -> serverTimestamp
inbox_data:{userId}        HASH   msgId -> InboxMessage JSON

outbox_order:{groupId}     ZSET   msgId -> serverTimestamp
outbox_data:{groupId}      HASH   msgId -> InboxMessage JSON

conv_order:{userId}        ZSET   convId -> lastMsgTime
conv_meta:{userId}         HASH   convId -> ConvSummary JSON
unread:{userId}            HASH   convId -> unread count

group_members:{groupId}    SET    userId
user_groups:{userId}       SET    groupId
group_member_info:{gid}    HASH   userId -> role/mute/version JSON
```

Redis Stream 建议使用单独的 key，例如：

```text
message_persist_stream
```

Stream event 至少包含：`eventId`、`serverMsgId`、`clientMsgId`、会话类型、发送者、目标、消息内容、消息类型、serverTimestamp 和 groupSeq。

第一阶段采用 Redis Standalone 或主从模式。Redis Cluster 下，群聊一次 Lua 更新多个用户 key 可能产生 `CROSSSLOT`，需要另行设计，暂不纳入本次改造。

## 6. Stream relay 生命周期与清理

### 6.1 relay 行为

主服务启动时创建 relay goroutine，并使用 Redis Consumer Group 读取 Stream：

1. 读取新消息。
2. 发布到 RabbitMQ。
3. 等待 publisher confirm。
4. confirm 成功后执行 `XACK`，再执行 `XDEL`。
5. 失败或超时不确认 Stream 消息，等待后续重试。

relay 重启时使用 `XAUTOCLAIM` 接管超时未处理的 pending 消息，避免某个旧 consumer 崩溃后事件永远停留在 Pending Entries List 中。

### 6.2 为什么不使用未确认消息 TTL

Redis Stream 没有安全的单条消息 TTL。对整个 Stream 设置过期时间，可能在 RabbitMQ 故障时删除还没有发送的事件。因此：

- 未确认事件不能依赖 TTL 删除。
- 正常事件在 RabbitMQ confirm 后立即 `XACK + XDEL`。
- 定时任务只清理 confirm 后残留的历史事件。
- 需要监控 Stream 长度、pending 数量和最老 pending 的年龄。

如果未来改成“必须等 MySQL 确认后才删除 Stream”，则需要 MySQL 消费者反向写入持久化确认事件，增加一条反馈链路；本次不采用该复杂方案。

## 7. RabbitMQ 可靠性

RabbitMQ 队列保持 durable，消息使用 persistent delivery mode。发布端必须启用 publisher confirm；仅 `PublishWithContext` 返回成功不能作为可靠确认。

建议同时处理：

- publisher confirm nack。
- mandatory publish 的 returned message。
- RabbitMQ 连接断开时的重连和 relay 暂停。
- 消费者成功写 MySQL 后才 ACK。
- 临时 MySQL 错误采用有界重试和延迟重试；超过次数进入死信队列，避免 `Nack(requeue=true)` 高速空转。
- JSON 格式错误等永久错误进入死信队列，不无限重试。

## 8. MySQL 幂等落库

`private_messages.id` 和 `group_messages.id` 继续使用 serverMsgId 作为主键。消费者重复收到同一事件时：

- 如果主键记录不存在，插入消息。
- 如果记录已存在且内容一致，视为成功并 ACK。
- 如果同一 serverMsgId 对应内容不一致，进入异常/死信处理，不能覆盖原消息。

建议在消息表增加可选的 `client_msg_id` 字段和普通索引，便于排查和客户端对账；幂等主键仍然使用 serverMsgId，不用 clientMsgId 作为长期唯一键，因为当前 clientMsgId 去重窗口只有 5 分钟。

## 9. WebSocket 回执与同步

RabbitMQ confirm 成功后：

1. 向发送方发送 `serverAck`。
2. 向在线接收方或在线群成员发送 `msg`。

如果 WebSocket 不在线、连接已失效或 `SendCh` 已满，不阻塞消息主链路；客户端通过 `syncReq` 补拉。

为支持断线后对账，建议 `InboxMessage` 也保留 `clientMsgId`。客户端展示消息时以 `serverMsgId` 去重，并用 `clientMsgId` 把异步回执对应到本地发送中的消息。

群聊 `readAck` 建议携带 `lastReadGroupSeq`，服务端保存用户在该群的阅读游标，而不是简单把未读数清零。`deliverAck` 第一阶段只做在线送达统计，不作为消息持久化状态。

## 10. 群成员一致性

由于发送鉴权依赖 Redis 群成员集合，群成员新增、移除、禁言和角色变化都必须同步维护 Redis：

- Redis 更新失败时，管理操作不能只记录日志后返回成功。
- 发送 Lua 脚本必须看到最新的成员状态。
- Redis 缓存缺失时，Go 层从 MySQL 加载成员集合并设置“已初始化”标记，然后重试 Lua。
- 群成员移除需要在发送路径上立即生效；MySQL 与 Redis 的更新失败需要补偿和告警。

群成员操作的严格一致实现方式需要和现有 GroupService 一并调整，不能只改消息发送脚本。

## 11. 故障行为

| 故障位置 | 预期行为 |
|---|---|
| Lua 校验失败 | 不写状态，不写 Stream，返回业务错误 |
| Redis Lua 成功，relay 未运行 | 消息可同步，Stream 保留，服务恢复后继续发 MQ |
| RabbitMQ confirm 超时 | 不 XACK/XDEL，不发 serverAck，relay 后续重试 |
| confirm 成功后进程崩溃 | 允许 MQ 重复消息，MySQL 通过 serverMsgId 幂等 |
| MySQL 暂时不可用 | RabbitMQ 保留消息并重试，不影响 Redis 同步 |
| WebSocket 推送失败 | 消息仍保留在 Redis，客户端下次同步补回 |
| Stream 出现坏消息 | 不 requeue 无限循环，进入死信并告警 |

## 12. 迁移与实施阶段

### 阶段一：基础能力

- 增加新的 Redis 数据结构和 Lua 脚本。
- 增加 Redis Stream event 格式。
- 增加 publisher confirm 支持。
- 增加 MySQL 幂等插入和必要字段。
- 完成 Lua、relay、消费者故障测试。

### 阶段二：消息写入切换

- 将私聊发送切换为 Lua 写 Redis 状态 + XADD。
- 停止私聊消费者写 Redis，只保留 MySQL 落库。
- relay confirm 后负责 serverAck 和实时推送。

### 阶段三：群聊发送切换

- 切换群成员校验、群发件箱、会话和未读原子更新。
- 增加群成员缓存初始化、更新和补偿。
- 压测不同群规模下 Lua 执行耗时。

### 阶段四：协议与运维完善

- `InboxMessage` 增加 clientMsgId。
- 群聊 readAck 增加 groupSeq 游标。
- 增加 pending、Stream 堆积、publisher confirm、MQ 重试、MySQL 死信等指标。
- 增加开关，支持必要时回退旧链路。

切换期间不能让旧消费者和新 Lua 同时重复写 Redis，否则会重复增加未读数、重复更新会话和推送。应使用功能开关按会话类型逐步切换，并在新链路稳定后关闭旧写入逻辑。

## 13. 批准前的默认项

如果没有额外要求，本设计默认：

- relay 与主服务共进程。
- RabbitMQ confirm 成功后立即 `XACK + XDEL`。
- MySQL 只按 serverMsgId 幂等，不等待 MySQL 反向确认 Stream。
- 群上限暂维持 500，并先压测单 Lua fanout。
- Redis 使用 Standalone/主从，不支持 Cluster 跨 key 原子群 fanout。
- serverTimestamp 由 Redis 生成。
- `deliverAck` 暂不持久化，群聊已读使用 groupSeq 游标。
- Redis 消息保留近期窗口，超出窗口的历史查询由 MySQL 提供回查能力。
