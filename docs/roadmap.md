# IM 重构路线图

目标是逐步构建一个面向少量受邀用户、通过浏览器使用的即时通讯系统。先完成基础聊天，再根据实际使用结果演进架构和扩展功能。

本文只记录总体方向、版本顺序和协作方式。每个小版本先确定要做什么；具体需求、技术方案和验收标准在该版本开始前讨论，记录到对应的版本文档中。

版本统一使用 `vx.x`，例如 `v0.1`、`v0.2`，不拆分三段式版本。版本号表达建设顺序，后续可以根据讨论和验收结果调整范围。

## 项目边界

- **仅提供 Web 应用。** 用户在浏览器输入网址即可使用，不制作可下载安装的桌面或移动客户端。
- **前后端分模块。** `backend/` 放后端服务，`frontend/` 放浏览器前端；跨模块配置、文档和部署编排可以放根目录，模块专属配置留在对应模块内。
- **面向桌面和手机浏览器。** 响应式布局与功能开发同步推进。
- **当前版本先做基础 IM。** 朋友圈、图片和文件消息、音视频等扩展能力留到后续阶段按需讨论。

## 大阶段

| 阶段 | 核心目标 |
| --- | --- |
| v0.x | 完成基础 IM 最小可用版本，供少量受邀用户实际体验。 |
| v1.x | 在基础 IM 上演进高并发、高可用架构。 |
| v2.x | 根据实际需求增加附属功能。 |

v1.x 和 v2.x 目前只保留方向，不提前拆分小版本或锁定技术组件。

## 已确认的基础行为

- **账号与好友：** 用户名密码注册登录，好友申请被接受后才能私聊；删除好友后双方不能继续发送新消息，历史保留。
- **文本与历史：** 支持文字、换行和表情字符，每条最多 2000 字；历史保存在服务端，分页查看，不主动按时间清理。v0 暂不做消息搜索、撤回和删除。
- **已发送：** 服务端保存消息成功并返回确认后，消息视为已发送；重复发送同一条消息不会重复保存。
- **已读：** 接收方进入双方聊天框时，当前已有消息视为已读；停留在前台聊天框时收到的新消息也自动已读。后台页面收到消息不自动已读。
- **展示保持简单：** 等待确认时提示发送中，异常时支持重试；不额外展示“未确认”或独立的“已送达”状态。
- **单聊天连接：** 同一账号只保留一个在线聊天连接，新连接会替换旧连接，包括第二个浏览器标签页。

这些行为作为后续版本讨论的共同前提，具体实现机制届时再确定。

## 文档组织约定

- **总体路线图：** 本文维护大阶段、小版本目标、跨版本原则及版本文档索引。
- **版本文档：** 统一放在 `docs/versions/v0.x.md`，每版一个文档，随讨论持续更新。
- **按需创建：** 开始讨论某一版时再创建对应文档；尚未开始的版本只保留路线图条目，不提前生成空文档。
- **明确状态：** 区分已确认事项、方案草案、待讨论问题、实现进展和验收记录，不把建议当作已确认或已完成功能。
- **保持路线图简明：** 接口、数据结构、组件选择和详细验收场景写入当前版本文档，不在路线图中提前展开。

## 贯穿各版本的建设方式

- **前后端按功能推进。** 每版形成能从浏览器操作和观察的结果，后端与对应前端一起验证。
- **基础正确性随功能交付。** 权限校验、消息保存、保存后确认和重试去重从相关功能首次实现时处理，不留到 v1.x 才补齐。
- **适配与验证持续进行。** 桌面和手机浏览器适配、相关测试和真实操作验证贯穿各版；v0.7 负责集中联调与部署收尾。
- **按当前需要选择架构。** v0.x 优先保证基础 IM 可用，技术组件到对应版本讨论，不预先搬回旧项目的全部依赖。
- **小步同步远程。** 在 `refactor/im` 上，每完成一个可验证的小改动，就检查、commit 并 push 到 `origin/refactor/im`；一个版本可以包含多次提交。

## 每个版本的协作节奏

1. **讨论当前版本：** 对齐范围、行为规则与验收场景，创建或更新对应版本文档。
2. **实现并运行：** 分小步完成当前能力，验证后及时提交推送。
3. **一起验收：** 从浏览器检查正常流程和关键异常场景，修正发现的问题。
4. **记录实际结果：** 保留最终方案、必要取舍、验收结果与当前限制。
5. **再进入下一版：** 根据本版实际结果调整下一版范围，再展开细节。
