# v1.7 群聊已读与 WebSocket 隐式已读

状态：方案已确认，尚未实现（2026-10-28）。

## 目标

把群聊的读状态（已读位置、未读数、已读人数）迁到 Redis，并让私聊和群聊的前台已读都由 WebSocket 隐式完成：

- 发送者能看到自己最后一条群消息被多少人读了；
- 每个成员能看到准确的群未读数，包含已接纳但尚未落 MySQL 的消息；
- 群聊的标记已读、未读计算和已读人数查询不查 MySQL；
- 用户停留在会话里时，已读位置自动保持最新，浏览器不再持续发送已读请求；
- 用户可见的已读规则保持 v0.5/v0.6 基线：进入会话即已读，后台页面不自动已读。

## 范围变化

路线图原定 v1.7 只做群聊已读。讨论中确定把前台已读机制一并改为 WebSocket 隐式已读，私聊和群聊统一：

- v1.6 的前台持续上报是“收到消息后约 1 秒内发一次 HTTP 请求”。空闲时没有请求，但请求数约等于送达前台观看者的消息数，群聊里按成员数放大，每个请求还要走一次 MySQL 鉴权；
- 隐式已读让前台持续阅读不再产生读请求，鉴权只在建立连接时做一次；
- 代价是 v1.6 前端的持续上报和离线待上报队列基本被取代。v1.6 的 Redis 位置模型和异步落库保留，HTTP 已读接口保留给兼容和回滚。

## 已确认的产品预期

效果参考飞书的群已读：每个人能看到自己发出的消息被多少人读了，也能知道自己还有多少未读。

1. 只在自己的消息上显示已读进度，且只显示当前会话里**最后一条发送成功的自己的消息**。私聊和群聊规则相同。
2. 私聊文案保持 `已读` / `未读`；群聊文案为 `已读 3/5`，全部已读时显示 `全部已读`。分子分母都不含自己。
3. 不显示已读/未读成员名单，只显示人数；别人发的消息不显示已读人数。
4. 群里只剩自己时不显示已读进度；发送中和发送失败的消息不显示。
5. 回执只挂在屏幕上已加载的消息下面。最后一条自己的消息滚出已加载范围时暂不显示，翻到那条消息时再出现（私聊现在也是这样）。
6. 群会话列表只显示未读数，不显示已读进度。
7. 进入会话或在前台停留时自动已读，后台页面不自动已读，回到前台一次补齐（沿用 v0.5/v0.6）。
8. 发送消息等于读到了这里：自己的已读位置会推进到自己发出的消息。
9. 新成员入群时，当前已有的群消息视为已读；成员退群或被踢后立即从分母中去掉。分母始终是“当前群成员减自己”，不做发送时的成员快照。
10. 有人读了之后，发送者当前打开的群里数字会更新（秒级），不弹窗、不提示音。

## 决策状态

- **已确认：** 上面的产品预期；已读位置用 Redis 有序集合；发送即已读且异步推进，不放进消息接纳的 Lua；WebSocket 隐式已读；`focus` 时服务端直接推进到最新；已读人数由客户端传消息号、服务端校验归属，老消息回落 MySQL 查一行；回执只挂已加载消息。
- **方案草案（按推荐补全，实现前复核）：** 合并窗口、异步落库合并、`group.read` 信号细节、成员变化接线、回填与切换、失败降级、HTTP 接口保留范围。

## 数据模型

### Redis

| 键 | 类型 | 内容 |
| --- | --- | --- |
| `group:{G}:read` | ZSET | member 为 userID，score 为该成员最后已读消息号 |
| `group:{G}:inbox` | ZSET | 复用 v1.3：群内全部已接纳消息号 |
| `group:{G}:members` | SET | 复用 v1.3：当前成员集合 |
| `group-messages:{id}` | HASH | 复用 v1.3：消息实体，含 `group_id`、`sender_id` |
| `group-read:stream` | Stream | 群已读位置变更事件，供异步持久化 |
| `group-read:ready` | STRING | 历史回填完成标记 |

- 键名沿用现有 keyspace，正式环境带 `im:v12:` 前缀，验证环境带 `im:v13-verify:` 前缀。
- 已读位置不设 TTL，容量治理留到 v1.9；`group-read:stream` 使用 `MAXLEN ~ 10000`。
- 不新增“自己发过的消息”索引和“最后一条自己的消息”索引，不维护未读计数器。

流事件字段：

```text
group_id、user_id、last_read_message_id、updated_at_ms
```

### MySQL

- `group_members.last_read_message_id` 保持不变，不需要迁移。
- 异步写入：`UPDATE group_members SET last_read_message_id = GREATEST(last_read_message_id, ?) WHERE group_id = ? AND user_id = ?`；影响 0 行说明成员已退群，直接确认。
- MySQL 是持久化和重建来源，不在已读请求链路上。

## 隐式已读

### WebSocket 协议

现有 WebSocket 只有服务端推送，服务端读循环会丢弃客户端帧。v1.7 新增客户端帧：

```json
{"type":"focus","kind":"direct","username":"bob"}
{"type":"focus","kind":"group","group_id":12}
{"type":"blur"}
```

`focus` 的应答：

```json
{"type":"focus.ack","kind":"group","group_id":12,"last_read_message_id":345}
```

- 校验失败时应答带 `error`（例如 `not_friend`、`not_group_member`），该连接不设置焦点；
- 每个账号只有一条连接，焦点直接记在这条连接的内存里，不进 Redis，连接断开焦点自然消失；
- 客户端帧有大小限制和频率限制，防止滥用。

### 焦点生命周期

1. 打开会话、页面回到可见、重连成功时，客户端发送 `focus`。
2. 服务端校验权限，把焦点记在这条连接上，并立即把该成员的已读位置推进到该会话最新已接纳的消息，回 `focus.ack`。这沿用 v0.5“进入聊天框，当前已有消息视为已读”的规则，也避免消息恰好在 `focus` 处理前被推送而漏掉。
3. 之后该会话每有新消息推送给这条连接，服务端在推送之后异步推进该成员的已读位置。
4. 切换会话、页面隐藏、断线时焦点清除，后台收到的消息保持未读。

“在看”的定义与 v1.6 一致：选中了该会话、页面可见、连接正常。

### 推进方式

- 已读位置只增不减（`ZADD GT`），异步推进的乱序、重复都不会回退。
- **接纳链路不变。** 私聊和群聊消息接纳的 Lua 不写任何已读数据。
- **接收者：** 消息推送完成后，进程内的异步步骤找出焦点就是该会话的在线成员，推进他们的位置。群聊用一次批量脚本推进同一条消息的多个观看者；同一会话短时间内连续来的消息合并成一次，取最大消息号。
- **发送者：** 发送者是前台观看者，走与接收者相同的路径；另外在接纳返回后再异步补推一次发送者自己的位置，覆盖“刚发完就切走”和没有 `focus` 的 HTTP 客户端。
- 只有位置真正推进才写 `group-read:stream`、才发事件。
- 私聊沿用 v1.6 的 `dm:read` 模型，推进后发送 `messages.read`；群聊推进后发送 `group.read` 信号。

## 未读与已读人数

### 群未读

```text
pos     = ZSCORE group:{G}:read me，没有则 0
我的未读 = ZCOUNT group:{G}:inbox (pos +inf
```

- 发送者的位置由异步推进，通常会越过自己发的消息，所以不再维护“自己发的消息”索引来扣除。
- 未读包含已接纳但尚未落 MySQL 的消息。
- 会话列表和 bootstrap 的群未读改从 Redis pipeline 获取，去掉对应的 MySQL 群未读查询；群名、成员数和最后一条消息仍由 MySQL 提供。

### 已读人数

```text
GET /api/groups/:id/read-stats?message_id=m
```

响应：

```json
{ "message_id": 345, "read_count": 3, "member_count": 5, "all_read": false }
```

对已确认属于当前用户的消息 `m`，一个 Redis 事务内读取：

```text
是否成员   SISMEMBER group:{G}:members me
成员数     SCARD group:{G}:members
读到 m 的  ZCOUNT group:{G}:read m +inf
我的位置   ZSCORE group:{G}:read me

read_count   = ZCOUNT 结果；如果我的位置 >= m 则再减 1
member_count = 成员数 - 1
all_read     = member_count > 0 且 read_count >= member_count
```

- `read_count` 和 `member_count` 都不含发送者。发送者位置异步推进，可能尚未追上 `m`，所以要判断后再减 1。
- 分母用成员集合而不是 `group:{G}:read` 的大小，某个成员的位置记录缺失时按“未读”处理，不会把分母算小。
- 成员集合缺失、`sync_required` 或群已解散时返回错误，不给出可能不准的数字。

### 定位“最后一条自己的消息”

由客户端传入 `message_id`，它本来就知道屏幕上自己最后一条发送成功的消息。服务端不信任参数，校验消息归属：

1. 读取消息实体 `group-messages:{m}`，`group_id` 必须等于路径中的群，`sender_id` 必须等于当前用户；
2. 实体不存在（v1.3 之前的老消息，或 Redis 数据丢失后）时，回落 MySQL 按群和消息号查一行发送者；
3. 不是自己的消息返回错误，别人的消息不会泄露已读人数。

没有采用“接纳时写 `own-last`”：接纳 Lua 不再写已读相关内容，异步写入一旦丢失指针会停在旧消息上且不能自愈，还要多一次历史回填。

## 实时更新

成员的已读位置推进后，服务端向在线群成员广播：

```json
{"type":"group.read","group_id":12}
```

- 不带读者和已读位置，广播时排除读者本人；
- 发送者的客户端正在该群、屏幕上有自己的回执消息时，300ms 防抖后重新请求 `read-stats`；
- 离线、切换会话、重连后，打开群时重新拉取一次；
- 成员加入、退出、被踢复用现有 `group.changed`，客户端在成员变化时也刷新一次回执；
- 事件是尽力通知，丢失不影响正确性，下次打开或重连会校准；
- 私聊继续使用 `messages.read`，格式不变。

## 成员变化

- **建群：** 所有成员位置为 0。
- **入群：** MySQL 写入 `last_read_message_id = max(MySQL 最新群消息号, Redis last_accepted_id)`，Redis 写同一个值。v1.3 异步链路下 MySQL 最新消息号可能落后于已接纳消息，取较大值可避免新成员把入群前已接纳的消息算成未读。
- **踢人/退群：** MySQL 删除成员行，Redis 同时从成员集合和 `group:{G}:read` 中移除，分母立即变化。
- **解散：** 群不可访问，不再计算；键清理留到 v1.9。
- **启动重建：** 成员集合从 MySQL 重建；`group:{G}:read` 只为缺失成员补位置（来自 MySQL），不覆盖 Redis 已有的位置，避免把还没落库的新位置回退。
- 成员集合缺失或处于 `sync_required` 时，群已读、未读、已读人数返回 503，不继续放行。

## 异步持久化

- 后台 worker 使用 consumer group 消费 `group-read:stream`，按 `GREATEST` 写入 `group_members`；
- 同一成员在同一群的多个事件合并，只写最大位置，MySQL 写入量不随消息数线性增长；
- 成功后才确认；MySQL 临时错误退避重试；格式错误和外键/约束等永久错误记录日志后丢弃，避免阻塞；
- 成员已退群（影响 0 行）直接确认；
- Redis 是读状态权威，MySQL 异步跟上；Stream 被裁剪导致事件丢失时 MySQL 会短暂落后，对账留到 v1.8。

## 历史回填与上线切换

一次性命令，幂等：

```bash
/opt/IM-Rebuild/imctl --verify backfill-group-read
/opt/IM-Rebuild/imctl backfill-group-read
```

1. 把所有历史群消息号写入 `group:{G}:inbox`（只写消息号，不写消息实体）；
2. 把 `group_members.last_read_message_id` 写入 `group:{G}:read`；位置取 `max(已读位置, 该成员在该群自己发的最后一条消息号)`，并用 `GREATEST` 写回 MySQL，保持“发送即已读”，避免上线后成员自己的老消息被算成自己的未读；
3. 重建成员集合；
4. 校验：每个群的 MySQL 消息号都存在于 inbox，成员数与 `group:{G}:read` 条目数一致，位置不小于 MySQL；
5. 通过后写入 `group-read:ready`，并记录 Redis 内存增量。

启用群消息链路时，缺少 `group-read:ready` 后端拒绝启动；运行期读状态接口缺少标记返回 503。Redis 数据丢失后需要重新回填。

**切换顺序。** v1.6 的群聊发送不维护新的读状态，群已读只写 MySQL。如果边运行 v1.6 边回填，回填之后的新消息和新已读会漏。所以正式切换和 8199 验证都按下面顺序：备份 → 停后端 → 替换文件 → 回填 → 启动。停机期间没有新消息和新已读，回填窗口是闭合的。回填命令只依赖 MySQL 和 Redis，不需要后端在运行。

## 接口与兼容

| 接口 | 变化 |
| --- | --- |
| WebSocket `focus` / `blur` / `focus.ack` | 新增 |
| WebSocket `group.read` | 新增事件 |
| `GET /api/groups/:id/read-stats` | 新增 |
| `POST /api/groups/:id/read?through_id=N` | 保留，内部改用 Redis 推进逻辑，供旧客户端和回滚使用 |
| `POST /api/conversations/:username/read`、`POST /api/read` | 保留，行为不变，不扩展群聊 |
| `GET /api/conversations`、`POST /api/bootstrap` | 群未读改为从 Redis 读取 |
| `messages.read`、`group.message.created`、`group.changed` | 格式不变 |

前端不再主动调用上述 HTTP 已读接口，它们只用于兼容和回滚。

## 前端

- 打开会话、页面可见、重连成功时发送 `focus`（切换会话直接发新的 `focus` 覆盖旧的），页面隐藏时发送 `blur`；收到 `focus.ack` 后用其中的位置清除本地未读；
- 退役 v1.6 的持续上报（来消息后按 1 秒节流上报）和离线待上报队列；离线阅读后重连，重新 `focus` 即由服务端补齐；
- 群聊最后一条自己发送成功的消息下显示 `已读 3/5` / `全部已读`；打开群、发送消息后、收到 `group.read`（300ms 防抖）、成员变化、页面重新可见和重连后请求 `read-stats`；
- 请求结果按 `message_id` 对账，回执只显示在对应消息上，切换会话时清除；
- 私聊回执保持 `已读` / `未读`，数据来源不变。

## 失败与降级

| 场景 | 行为 |
| --- | --- |
| Redis 不可用 | 群已读、未读、`read-stats` 和 `focus` 返回错误，不回落 MySQL；群发送本来就会失败 |
| MySQL 不可用 | 位置、未读和已读人数照常；异步落库积压重试；会话列表和历史按现有逻辑失败 |
| 回填未完成或 Redis 丢数据 | 读状态接口 503，重新回填后恢复 |
| `focus` 或推送后的推进丢失 | 位置暂时落后；下一次 `focus`、重连或发送消息后追上，不会永久错误 |
| 刚发完消息就切走且补推失败 | 自己的消息可能短暂算成自己的未读，下次打开会话恢复 |
| `group.read` 事件丢失 | 数字暂时偏旧；打开、重连或页面重新可见时校准 |
| Stream 积压或裁剪 | Redis 仍是权威，MySQL 短暂落后；对账留到 v1.8 |

## 验收方向

1. A 在群里发消息，B、C 在前台打开该群：A 的最后一条消息下 `已读 0/2` 很快变为 `已读 2/2` 并显示 `全部已读`，期间不需要刷新。
2. B 在后台页面时 A 发的消息保持未读，B 回到前台后一次补齐，A 的人数随之更新。
3. 只有 A 最后一条自己的消息显示回执；A 再发一条后回执移到新消息上，旧消息不再显示。
4. 别人的消息、发送中和失败的消息不显示回执；`read-stats` 传入别人的消息号被拒绝。
5. 踢掉没读的人，分母变小；踢掉唯一没读的人，显示 `全部已读`；新成员入群后历史消息不产生未读。
6. 消息已接纳但尚未落 MySQL 时，未读和已读人数仍然正确，落库后不变化。
7. 会话列表中每个群的未读数逐项正确，上线时不查询 MySQL 的群未读。
8. 前台停留在会话里持续收消息，浏览器不发送任何已读 HTTP 请求，已读位置仍然保持最新。
9. 离线后重连，位置由 `focus` 补齐；刷新页面后未读不闪回。
10. 刚发完消息立即切走，自己的未读最终为 0。
11. Redis 不可用时群已读相关接口明确失败，恢复并回填后继续工作；MySQL 不可用时已读照常。
12. 私聊已读回执、v1.6 行为和群聊消息收发、历史、成员管理不变。
13. 回填后老群的未读和已读位置与切换前一致，缺少 `group-read:ready` 时后端拒绝启动。

## 不在本版范围

- 已读/未读成员名单、逐条消息的已读回执；
- “滚动到底才算已读”；
- 多设备同时在线和多标签同步；
- 服务端定向推送聚合人数（目前是广播信号加重拉）；
- 多实例 WebSocket 的焦点归属、可靠投递、对账和 pending 接管（v1.8）；
- 已读键 TTL、容量治理和压力测试（v1.9）；
- 鉴权会话缓存。

## 风险

1. **服务端成本转移。** 隐式已读把持续上报的 HTTP 请求变成服务端推进：群里有 k 个前台观看者，一条消息就要推进 k 个位置。靠批量脚本、短窗口合并和落库合并压住，实际成本留到 v1.9 实测。
2. **“推送到”不等于“已渲染”。** 隐式已读按推送计算，页面渲染失败或浏览器节流时，位置可能略超前于用户实际看到的消息。
3. **`group.read` 广播放大。** 100 人群里一次已读最多触发几十个 `read-stats` 请求，靠防抖和每次只有几条 Redis 命令控制；压力大时再改为服务端定向推送聚合人数。
4. **回填窗口。** 切换必须停后端后回填，否则会漏掉回填之后产生的群消息和已读。
5. **老消息归属校验回落 MySQL。** 极少数场景下 `read-stats` 会查一行 MySQL，只在最后一条自己的消息是 v1.3 之前的老消息或 Redis 丢数据后触发。
6. **Redis 丢数据会丢最近已读。** 异步落库有窗口，重建后以 MySQL 为准，用户可能看到少量未读回来；对账和恢复留到 v1.8。
7. **v1.6 前端部分被取代。** 隐式已读上线后，v1.6 的持续上报、离线队列和相关 smoke 用例需要同步调整；回滚到 v1.6 前端时仍可使用保留的 HTTP 接口。
8. **Redis 内存继续增长。** 群 inbox 回填会让键明显变大，已读位置随群数和成员数增长；上限仍是 64 MiB + noeviction，容量治理留到 v1.9。
