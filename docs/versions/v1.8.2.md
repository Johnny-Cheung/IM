# v1.8.2 可靠投递与对账

状态：方案草案，待确认（2026-10-29）。属于 [v1.8 可靠性与一致性](v1.8.md)，依赖 [v1.8.1](v1.8.1.md) 的会话消息号 `seq`。

## 目标

让已经被 Redis 接纳的消息一定能落到 MySQL：进程重启、RabbitMQ 或 MySQL 短暂不可用、个别消息落库失败时，消息不会卡在 Redis 里，也不会堵住整条队列；仍然出现的不一致能被发现，并在有条件时自动补上。

范围只含单体：一个后端进程、一台 Redis、一台 RabbitMQ、一个 MySQL。

## 背景

私聊和群聊各有一条结构相同的链路：

接纳 Lua（原子写入实体、索引、幂等记录和 Stream 事件）→ relay 读 Stream，发布到 RabbitMQ 并等 broker 确认，确认后 `XACK` 加 `XDEL` → consumer 从队列取出并写 MySQL，写成功后才 ack。

已经可靠的部分：

- 接纳在一次 Lua 里原子完成；
- RabbitMQ 交换机和队列持久，消息持久，发布带确认，consumer 手动 ack；
- MySQL 落库按全局消息号、客户端 ID、（会话，`seq`）三重幂等，重复投递不会重复入库。

读取代码核对出的缺口：

1. **relay 的待确认条目不会被重读。** relay 只读新条目（`>`），不重读自己已读取但未确认的条目。RabbitMQ 发布失败、断连、broker 拒绝确认，或后端在等待确认时被停止（此时直接返回，不 ack），这条消息会一直留在 Stream 的待确认列表里：Redis 里能读到，永远进不了 MySQL。读水位的 persister 已有 `drainPending`，消息 relay 没有。日常重启和部署也可能触发。
2. **consumer 对任何非冲突错误都立即重新入队，没有退避，也没有次数上限。** 永久错误（例如外键 1452，`PersistMessage` 没有单独处理）会无限重试；prefetch 为 1，一条这样的消息会堵死整条队列。
3. **没有死信队列。** 毒消息要么被丢弃，要么堵队列，事后也无处查看。
4. **Stream 写入带 `MAXLEN ~ 10000`。** relay 停得足够久、积压超过约一万条时，尚未转发的条目会被近似裁剪掉。
5. **没有兜底对账。** 上面任何一处出问题，系统自己发现不了。v1.8.1 之后“会话内条数等于最大 `seq`”可以作为低成本的检查依据。
6. **观测缺口。** 看不到 Stream 待确认数、最老未转发年龄和死信数。
7. **吞吐。** relay 逐条等确认，consumer prefetch 为 1。这属于容量问题，留给 v1.9。

## 已确认决策

1. **只做单体。** 不考虑多实例、多 consumer 竞争和 pending 跨进程接管。这条同时写入 [v1.8 总览](v1.8.md)。
2. **范围包含对账。** relay 恢复、Stream 不裁剪、consumer 重试与分类、死信队列、观测和兜底对账放在同一个子版本。
3. **重试在进程内做。** 不改 RabbitMQ 拓扑，不引入延迟队列。指数退避，只对“与这条消息有关”的错误计次，最多 5 次，约 30 秒后进死信。MySQL 连接失败、超时、死锁这类暂时错误不计次数，持续退避重试到恢复，否则 MySQL 重启一分钟就会把正常消息批量送进死信。
4. **Stream 不再裁剪。** 靠报警发现积压，内存上限留到 v1.9。relay 转发成功后会 `XDEL`，Stream 里只剩未转发的条目。
5. **对账能补就补，补不了就写日志。** 不删除任何数据，不修改 Redis 计数器（计数器由 v1.8.1 的校准器负责）。
6. **持久化级别、接纳语义和“不做向后兼容”沿用 v1.8 总览。**

## 方案草案

以下细节由我提出，尚未逐项确认。

### relay 恢复（A）

- relay 启动和每次重连后，先用 ID `0` 读取自己的待确认条目，逐条重新发布并确认，处理完再读新条目，做法与已读 persister 的 `drainPending` 一致。
- 停机时正在等待确认的条目不 ack，留在待确认列表，下次启动由上面的步骤接管。重复发布由 consumer 的幂等落库吸收。
- 发布失败时不丢弃条目，退避后重试同一条。

### Stream 不裁剪（B）

- 接纳时去掉 `MAXLEN ~` 裁剪。
- Stream 中未转发条目超过阈值（暂定 1000 条），或最老条目超过 60 秒未转发时，`/ops/infra` 标记告警并写日志。

### consumer 错误分类与重试（C）

| 错误类型 | 处理 |
| --- | --- |
| MySQL 连接失败、超时、死锁、锁等待超时 | 不计次数，指数退避重试（单次间隔上限 30 秒），直到成功 |
| 与消息有关的错误：外键失败、数据超长、其他未知错误 | 退避 1、2、4、8、16 秒共 5 次，仍失败则进死信 |
| 消息无法解码、正文冲突、`seq` 冲突 | 不重试，直接进死信（v1.8.1 对冲突只记日志并确认，改为进死信以便事后查看） |

- 重试期间 consumer 一直持有这条消息，不 ack；进程中途退出时 broker 会重新投递，计数从头开始。
- 进死信的动作：consumer 带着原因、尝试次数和首次失败时间，把原消息发布到死信交换机并等待确认，成功后才 ack 原消息。主队列的声明参数不变，避免 `PRECONDITION_FAILED`，因此不使用 RabbitMQ policy。

### 死信队列（D）

- 私聊和群聊各一个死信队列，持久，不设 TTL，不自动消费。
- 死信消息体保持原样，消息头带原因、尝试次数、首次失败时间和来源链路。
- `imctl` 增加 `dlq-list`、`dlq-replay`、`dlq-discard`：查看、按条或全部重放、丢弃。重放把原消息重新发布到主交换机，走正常链路，幂等落库保证重复无害。丢弃需要明确的确认参数。

### 观测（E）

`/ops/infra` 的消息链路部分增加：Stream 长度、待确认数、最老未转发年龄、死信数、最近一次 relay 和 consumer 错误、最近一次对账的时间与结果。

### 兜底对账（F）

后端进程内的一个后台任务：校准完成、闸门打开后运行一次，之后每 5 分钟一次；闸门关闭期间跳过。

1. 一次查询取出 MySQL 每个会话的 `COUNT(*)` 和 `MAX(seq)`，另用 pipeline 读 Redis 计数器。
2. 只对“Redis 计数器大于 MySQL `MAX(seq)`”或“`COUNT(*)` 不等于 `MAX(seq)`”的会话取细节：列出 MySQL 已有的 `seq`，与 `1..计数器` 比较，得到缺失的 `seq`。
3. 对每个缺失的 `seq`，从会话索引（`dm:pair`、`group:{G}:inbox`）取全局消息号，再读消息实体。实体创建时间距今不足 5 分钟的跳过，视为仍在途。
4. 其余缺失项**自动补**：调用 consumer 使用的同一个幂等落库方法直接写 MySQL，不经过 Stream 和队列。这样不依赖 relay 和队列状态，也不会和死信队列互相循环。
5. **补不了**的写 error 日志，并计入 `/ops/infra` 的未解决数：实体或索引在 Redis 里已不存在、字段不全，或落库遇到永久错误。同一（会话，`seq`）每小时最多记一条日志。
6. 对账只补 MySQL，不修改 Redis 的计数器、索引和水位，也不删除任何数据。

## 失败与降级

| 场景 | 行为 |
| --- | --- |
| 后端在 relay 等待确认时停止 | 条目留在待确认列表，下次启动先重发，消息最终落库 |
| RabbitMQ 不可用 | relay 退避重试，Stream 积压；超过阈值时 `/ops/infra` 告警；恢复后继续 |
| MySQL 短暂不可用 | consumer 不计次数地退避重试，不进死信；恢复后继续 |
| 单条消息永久落库失败 | 重试 5 次后进死信，其后的消息继续；对账会尝试补一次，仍失败则只写日志 |
| 死信发布失败 | 不 ack 原消息，按暂时错误处理，退避后重试 |
| Redis 里的实体已丢失（掉电丢尾等） | 对账无法补，写日志；内容已丢失，不凭空生成 |

## 验收方向

1. 杀掉后端进程，使 relay 停在等待确认的位置，重启后该消息进入 MySQL，Stream 待确认数回到 0。
2. RabbitMQ 连接中断期间连续发送，恢复后全部落库，没有重复。
3. MySQL 不可用超过 1 分钟再恢复，消息全部落库，死信数为 0。
4. 构造一条必然落库失败的消息（例如落库前删除发送者账号），重试 5 次后进死信，后面的消息不受影响；`dlq-list` 可见，`dlq-replay` 可重放，`dlq-discard` 可丢弃。
5. 积压超过阈值时 `/ops/infra` 告警，Stream 条目不被裁剪。
6. 手工删除 MySQL 里一条已落库的消息：对账在超过 5 分钟后用 Redis 实体补回；再删除 Redis 实体后重复，对账只写一条日志。
7. v1.8.1 行为不变：`seq` 连续、未读、已读、校准。

## 不在本版范围

- 跨实例、多 consumer、pending 跨进程接管（单体决定）；
- Redis 数据整体丢失后从 MySQL 重建 Redis（后续子版本再讨论）；
- relay 批量确认、consumer 并发和 prefetch 调优、Stream 容量治理（v1.9）；
- RabbitMQ 延迟队列。

## 风险

1. **自动补和正常落库可能同时写同一条消息。** 依赖三重幂等和唯一索引吸收，需要并发测试。
2. **毒消息会短暂阻塞队列。** 单条最多约 31 秒，因为 prefetch 为 1 且重试在进程内。
3. **不裁剪的 Stream 在 relay 长期停止时会持续占用内存。** 靠告警发现，上限留到 v1.9。
4. **死信重放可能再次失败。** 重放不改变消息，原因没有消除时会重新进死信。
5. **对账的 SQL 在会话很多时需要分页。** 实现时控制批大小。
6. **故障演练会影响共用容器的 8198。** 8198 和 8199 共用同一个 MySQL、Redis 和 RabbitMQ 容器，停容器的演练需要单独确认；能在验证 vhost、验证库或验证命名空间内完成的（断开验证 vhost 的连接、对验证库加锁）优先。

## 实施小步

1. messaging：relay 恢复，去掉 Stream 裁剪，consumer 错误分类、重试和死信发布，死信拓扑；
2. store：对账所需查询（每会话条数与最大 `seq`、缺失 `seq` 的列举）；
3. messaging：对账任务；
4. httpapi 与 cmd：`/ops/infra` 字段，对账任务装配；
5. `imctl`：`dlq-list`、`dlq-replay`、`dlq-discard`；
6. 验证：`go test`、`go vet`、`-race`，独立对抗审查；
7. 8199 隔离验证：按验收方向逐项演练，故障只在验证 vhost、验证库和验证命名空间内制造。
