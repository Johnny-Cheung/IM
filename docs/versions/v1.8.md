# v1.8 可靠性与一致性

状态：进行中（2026-10-28 开始），按子版本逐个模块推进。

## 目标

让消息和已读链路在多实例运行、进程崩溃、Redis 重启或数据丢失时仍然正确：不丢已确认的消息，不重复，不串权限，不出现假已读；出现不一致时能发现、能修复。

## 推进方式

v1.8 不预先固定模块数量。每次只讨论一个要优化的模块，方案确认后记录为一个子版本 `v1.8.x`，随后开发、隔离验证、切换正式环境，再讨论下一个。

- 本文记录目标、跨子版本的共同决策和子版本索引；
- 每个子版本一份文档 `docs/versions/v1.8.x.md`，记录方案、实现进展和验收结果；
- 后面的子版本可以依赖前面已经交付的能力，依赖关系写在各自文档里；
- v1.8 的结束由双方共同判断：下面“待覆盖的问题范围”里的每一类问题都有结论，已解决，或明确留给后续版本。

## 待覆盖的问题范围

这些是 v1.7 结束时已知的、依赖单进程假设或只能尽力而为的环节。它们尚未讨论，不代表方案或顺序已经确定，每项在对应子版本开始前再讨论。

- 跨实例：WebSocket 广播、单账号单连接的替换、登出和改密后的连接关闭、焦点与隐式已读队列；
- 群成员投影写入的跨实例串行；
- 可靠投递：Stream、RabbitMQ、MySQL 之间的确认、重试、pending 接管和死信；
- Redis 与 MySQL 的对账，以及 Redis 数据丢失后的重建；
- 故障演练：杀进程、重启 Redis 和 RabbitMQ、MySQL 短暂不可用。

## 已确认的共同决策

1. **故障范围。** 基础设施只有一台开发机。v1.8 覆盖进程崩溃、容器重启、整机重启和掉电。整机或磁盘损坏只靠备份和 MySQL 重建恢复，不在同一台机器上放副本。
2. **持久化级别。** Redis 保持 AOF `appendfsync everysec`，不改为 `always`。`always` 会让每次写入等待落盘，而落盘发生在 Redis 主线程里，会拖慢所有命令，与 v1.x 的高并发方向冲突。
3. **接纳语义不变。** 消息写入 Redis 并返回确认即视为已发送。整机掉电或系统崩溃时，最多约 1 秒内已确认的消息可能丢失；Redis 进程或容器崩溃基本不丢。这是已知限制，写入文档，不试图消除。
4. **防线设计。** 在上述前提下，计数器与编号的校准、客户端按编号对账是主要手段，不是附加兜底。具体见 [v1.8.1](v1.8.1.md)。
5. **不做向后兼容。** 当前正式实例只有开发者本人使用，所有用户在 v1.x 全部开发完成后才开始使用。v1.8 各子版本中，接口、参数和字段直接替换，不为没有刷新的旧页面保留兼容。回滚靠切换前的备份和旧发布包。用户可见的行为基线仍以 v0.x 为准。

## 不在本版范围

- 新增产品功能；
- 容量验证、压力测试、Redis 键 TTL 和容量治理（v1.9）；
- 跨机器的高可用拓扑（如果后续有新增机器，再单独讨论）。
