# v2.1 朋友圈 Redis 缓存与推拉优化

状态：已通过 8199 隔离验证（2026-11-04），未切换正式 8198。MySQL 仍是朋友圈权威数据源；Redis 只保存可丢弃的 feed 索引和点赞快照，缓存缺失、过期或故障时自动回退 MySQL。本版不改 HTTP/WS 契约、不改 MySQL 表结构、不修改 `bench/`。

## 目标

- 朋友圈 feed 使用推拉结合：低好友数作者发布时写扩散到好友 feed，高好友数作者只维护作者时间线，由好友读取时拉取合并。
- 点赞使用 Redis Set 保存点赞用户，String 保存点赞计数；读取时补齐当前查看者的 `liked_by_me`。
- Redis 只做读加速，不参与发布、点赞、评论、删除的成功判定。
- 保持现有 `before_id`、点赞/评论游标、好友与私密可见性、软删除、点赞幂等和事务计数语义。
- 缓存清空或 Redis 故障时，朋友圈继续由 MySQL 提供正确结果。

## 不在本版

- 不缓存动态正文、作者昵称、评论预览、评论列表或未读红点。
- 不把点赞改为 Redis 先写、MQ 异步落库；点赞仍使用现有 MySQL 事务。
- 不改变 `moment.created` WebSocket 红点通知的 best-effort 语义。
- 不做多实例缓存失效、跨实例 Pub/Sub 或分布式锁。
- 不做自动对账/预热命令；缓存清空后按读取请求懒加载。

## Redis key

键名省略 namespace 前缀（正式 `im:v12:`，8199 为 `im:v13-verify:`）。所有 key 都由 `momentcache.Keyspace` 构造。

| key | 类型 | 作用 |
| --- | --- | --- |
| `moments:feed:{userID}` | ZSET | viewer 的最近可见 feed 快照；member/score 都是 moment ID |
| `moments:feed:meta:{userID}` | HASH | `floor`、`friends_hash`、`count` |
| `moments:feed:gen:{userID}` | STRING | 好友关系变化代际，防止旧 warm 覆盖新缓存 |
| `moments:feed:warm:{userID}` | STRING | viewer feed 单飞预热锁，短 TTL |
| `moments:feed:tmp:{userID}:{token}` | ZSET | 预热临时快照，完成后合并，短 TTL |
| `moments:author:{authorID}` | ZSET | 高 fanout 作者的 friends-visible 时间线，供 pull |
| `moments:author:meta:{authorID}` | HASH | `floor`、`count` |
| `moments:author:warm:{authorID}` | STRING | 作者时间线单飞预热锁 |
| `moments:author:tmp:{authorID}:{token}` | ZSET | 作者时间线临时快照 |
| `moments:pull-authors` | SET | 已进入 pull 模式的作者，sticky 只增不降 |
| `moments:likes:{momentID}:members` | SET | 点赞用户 ID 集合 |
| `moments:likes:{momentID}:count` | STRING | 点赞计数；存在即表示 Set 已完整预热 |
| `moments:likes:{momentID}:epoch` | STRING | 删除/重建点赞缓存时的失效代际 |

`moments:feed`/`moments:likes` 使用 TTL；`moments:author`、`moments:pull-authors` 也会在重建或清理时删除。它们都不是 MySQL 备份。

## Feed 读取

1. 先按当前 `friendships` 计算 friend hash，读取 viewer feed meta。
2. meta 缺失、friend hash 不匹配或 ZSET 数量不等于 `count` 时，从 MySQL `ListMoments(viewer, friends, 0, warmLimit)` 预热最近一页；warm 失败只回退 MySQL。
3. 读取 viewer feed，并合并 `moments:pull-authors ∩ 当前好友` 的作者时间线；高好友数作者的动态不在好友 feed 中，而是在这里拉取。
4. 各来源按 moment ID 倒序取候选，去重后调用 `ListVisibleMomentsByIDs`，重新按当前好友关系、visibility 和 `deleted_at` 过滤。
5. 只有能证明整页完整时才使用 Redis：
   - 可见候选至少 `limit+1` 条；
   - 请求游标没有跨过 `floor`；
   - 每一页不包含未预热的作者来源。
6. 其余情况（深分页、最后一页候选不足、删除后空洞、权限变化、Redis 错误）一律回退现有 MySQL `ListMoments`，`has_more` 和 `next_before_id` 仍以 MySQL 结果为准。

`floor=0` 表示预热已覆盖当前可见历史；`floor>0` 时只保证大于等于 floor 的区间完整。预热把 `floor` 和 `count` 写在 meta 中，发生删除或缓存缺失时通过回退 MySQL 保证不重不漏。写入新动态时 ZSET 按 `IM_MOMENTS_FEED_WARM_LIMIT` 裁剪最旧条目，并同步提高 `floor`；所有 feed/author key 都有 TTL。

## Feed 写入

- `CreateMoment` 先在 MySQL 提交，之后才写缓存。
- 作者自己的 feed 始终写入；private 动态只写作者自己的 feed，不进入公共作者时间线。
- friends-visible 动态写入 `moments:author:{author}`。
- 作者好友数 `<= pull_threshold` 时，动态 ID 写入每个好友的 `moments:feed`；超过阈值或作者已在 `moments:pull-authors` 时只保留作者时间线，由读取端 pull。
- 作者一旦进入 pull 模式不自动降回 push，避免好友数下降后历史动态出现缺口。
- 删除动态后从作者时间线、作者 feed 和当前好友 feed 中尽力 `ZREM`，并删除点赞缓存；读取端仍会再次校验 `deleted_at`，残留 ID 不会泄露已删除动态。
- 好友新增/删除成功后失效双方 feed、递增 generation，并设置进程内 dirty 标记；下一次读取回退并重新预热。好友变化 hook 通过 `MomentFriendshipCache` 可选接口接入，MySQL-only store 和测试 fake 不需要实现。

## 点赞缓存

- 写路径完全保留 `LikeMoment`/`UnlikeMoment` 的 MySQL 事务、唯一键和计数更新；HTTP 成功和响应计数始终以 MySQL 为准。
- 读取先检查 `count` key 和 Set 基数是否一致；一致才使用 Redis 计数和 `SISMEMBER`，否则用 MySQL 的 `like_count`/`liked_by_me`。
- 缓存未预热时，按动态批量读取 `moment_likes` 的完整用户集合，校验集合大小等于 `like_count` 后，通过 Redis 事务一次性安装 Set、count 和 TTL。
- MySQL 点赞提交后，如果缓存已预热，用 Lua 原子执行 `SADD`/`SREM` 并把计数设为 MySQL 返回的权威值；如果缓存未预热，不建立不完整 Set。
- 重复点赞/取消幂等；Set 基数与计数不一致时视为无效缓存并重新预热。
- Redis 更新失败时标记该动态为 dirty，读取绕过该动态的点赞缓存并回退 MySQL；进程内 dirty 在成功重装缓存后清除。
- 点赞列表分页继续使用 MySQL，因为现有接口按 `moment_likes.id` 排序，Redis Set 不保存该顺序。

## 一致性与降级

- 朋友圈缓存是 fail-open：Redis 错误不返回 5xx，只记录指标并回退 MySQL。与聊天消息“Redis 不可用时发送 503”的 fail-closed 语义不同。
- `moments:*` 不参与聊天 `seq:ready` 完整性门禁；`rebuild-redis` 只负责清理这些派生缓存，不要求重建成功才能写 `seq:ready`。
- 缓存缺失、TTL 到期、Redis 重启或命名空间清理后，下一次朋友圈读取从 MySQL 懒加载。
- 进程内 dirty 标记用于覆盖“MySQL 已提交、Redis 写失败”的窗口；进程重启会丢失 dirty 标记，此时由 TTL、下一次预热和 MySQL 回退兜底。无法取得作者好友列表时，当前进程持续使用 MySQL（`degraded=true`），直到重启。
- Redis 是单实例部署的读缓存；没有多实例一致性。若单 key 被 Redis 淘汰但计数仍满足校验，理论上可能出现页内空洞；生产部署应避免对 `moments:*` 使用随机驱逐策略，出现异常时清理 `moments:*` 并重新懒加载。
- 不缓存动态实体，因此昵称、正文、评论预览、评论计数始终来自 MySQL，改昵称或评论不需要失效 feed。

## 配置

```text
IM_MOMENTS_CACHE_ENABLED      默认 true；仅在 Redis 已配置时装配
IM_MOMENTS_PULL_THRESHOLD     默认 500
IM_MOMENTS_FEED_WARM_LIMIT    默认 500
IM_MOMENTS_FEED_TTL           默认 168h
IM_MOMENTS_LIKE_TTL           默认 168h
IM_MOMENTS_CACHE_TIMEOUT      默认 300ms
IM_MOMENTS_MAX_PULL_SOURCES   默认 100
```

Redis 未配置或 `IM_MOMENTS_CACHE_ENABLED=false` 时，`main.go` 直接注入 MySQL `store.Store`，朋友圈行为与 v2.0 相同。
