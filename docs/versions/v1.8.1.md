# v1.8.1 会话消息号与会话内水位

状态：开发完成，已通过 8199 隔离验证（2026-10-28），尚未切换正式 8198。属于 [v1.8 可靠性与一致性](v1.8.md)。

## 目标

给每个会话（一对好友的私聊、一个群）增加会话内连续递增的消息号，并以它为基础简化读模型：

- 未读数用两个数相减得到，不再对消息索引做 `ZCOUNT`；
- 私聊的两个方向合并成一个会话索引，历史分页只读一个 key；
- 客户端能通过编号发现丢失的消息和服务端回退；
- 为后续的对账和跨实例广播自愈提供依据：会话内消息条数应等于最大编号。

## 背景

- 当前全局消息号（Redis `INCR`，私聊和群聊共用）全局唯一，但在单个会话内不连续。客户端收到 120 号，无法判断 101 到 119 里有没有这个会话的消息，只能靠断线重连后按游标补拉兜底。
- 私聊未读是对 `dm:conv:{我}:{对方}` 做 `ZCOUNT`。该 key 按方向拆分，只含对方发给我的消息，一对好友有两个；会话历史要合并两个 key 再排序。
- 群聊未读是对 `group:{G}:inbox` 做 `ZCOUNT`。
- `ZCOUNT` 是 O(log N)，速度不是主要问题。主要收益是丢消息检测、对账和读路径简化。

## 已确认决策

1. **新增会话消息号 `seq`。** 每个会话从 1 开始，每接纳一条消息加 1，会话内单调连续、无空洞。它只在会话内唯一；全局唯一仍由现有全局消息号负责，（会话，`seq`）合起来全局唯一。上限 `MaxSafeSeq = 2^53 - 1`，超过时拒绝接纳。
2. **全局消息号保留。** 继续用于私聊 feed 增量同步、消息实体键、MySQL 主身份和跨会话唯一标识。
3. **会话的定义。** 私聊以“一对用户”为一个会话，由两人的内部用户 ID 确定（小的在前，记作 `low`、`high`）。删除好友再加回来，编号接着往下排，历史不断。群以群为一个会话。
4. **用 Redis 原子自增分配。** 在接纳 Lua 里，非好友、非成员、重复、正文冲突、编号溢出等拒绝判断全部完成之后，才对会话计数器加 1，与写入消息、索引、幂等记录在同一次原子执行内。重复发送命中幂等时返回原消息实体上的 `seq`，不再分配。
5. **私聊 `dm:conv` 二合一。** 一对好友一个会话索引 `dm:pair`，双方消息都进去，分数为 `seq`，成员为全局消息号，消息实体键不变。群 inbox 的分数也改为 `seq`。
6. **未读 = `last_seq - read_seq`。** 结果小于 0 按 0。私聊和群聊使用同一个公式。发送者的水位仍然异步推进，所以私聊刚发完的几十毫秒内，会话列表可能把自己的消息算成未读，下一次 `focus` 恢复；群聊本来就是这样。群的已读人数仍然是对成员水位做 `ZCOUNT`，不变。
7. **水位线的单位换成 `seq`。** Redis 里的私聊水位值、群水位的分数，以及 MySQL 的已读位置都改用 `seq`。
8. **持久化与故障前提沿用 v1.8 总览。** AOF 保持 `everysec`；启动和 Redis 重启后先校准计数器再接纳；客户端按编号对账。
9. **游标和参数直接换成 `seq`，不保留旧参数。** 单会话历史（私聊、群聊）的 `before_id`、`after_id` 改为 `before_seq`、`after_seq`；bootstrap 里每个群的游标改为 `after_seq`；`read-stats` 的 `message_id` 改为 `seq`；`focus.ack`、`messages.read` 里的 `last_read_message_id` 改名为 `last_read_seq`；会话列表里的 `peer_last_read_message_id` 改名为 `peer_last_read_seq`。私聊的 feed 增量同步仍用全局消息号 `after_id`。
10. **不做向后兼容。** 当前正式实例只有开发者本人使用，所有用户在 v1.x 全部开发完成后才开始使用，所以接口和字段直接替换。旧的 HTTP 已读接口（`POST /api/read`、`POST /api/conversations/:username/read`、`POST /api/groups/:id/read`）随之删除，已读只走 WebSocket `focus`。
11. **掉电丢尾后允许原客户端 ID 重发。** 客户端对账发现本地“已发送”的消息在服务端不存在时，把它转成发送失败状态（正文和客户端 ID 来自本地缓存的消息记录），沿用现有的失败重试入口。

### 影响面扫描后补充的决策

12. **MySQL 用普通列，不用生成列。** 当前 MySQL 8.4.11 在带 `ON DELETE CASCADE` 外键的表上不允许新增生成列（`v0.3.md` 已记录，错误 1215）。`messages` 新增应用层维护的可空列 `conversation_low_id`、`conversation_high_id` 和 `seq`，加（`low`、`high`、`seq`）唯一索引；`group_messages` 新增可空 `seq`，加（`group_id`、`seq`）唯一索引。可空列在回填前不会触发唯一冲突。不加 CHECK 约束。
13. **无 Redis 的本地模式。** 保留发送、历史和会话列表：在 MySQL 事务里用 `MAX(seq)+1` 分配，只限本地开发。已读不支持（WebSocket `focus` 返回 503，旧的 HTTP 已读接口已删除），未读数只按 MySQL 已有的 `last_read_seq` 统计对方发来的消息，不会随阅读清零。该限制写入 README 和运维文档。
14. **单一就绪标记 `seq:ready`。** 取代 `dm:read:ready` 和 `group-read:ready`。启用 Redis 消息链路时，缺少 `seq:ready` 后端拒绝启动；运行期间丢失则接纳和读状态返回 503。旧的 `backfill-read`、`backfill-group-read` 命令及其门禁一并删除，由 `backfill-seq` 取代，避免它们重建已废弃的结构。
15. **`dm:conv-last` 格式不变。** 仍是对方 → 最新消息的全局消息号，只用于会话列表的“最后一条消息”预览。会话的 `last_seq` 直接读会话计数器，不依赖消息实体是否在 Redis 里。
16. **热读按 `seq` 区间进行，不再用 epoch。** 回填后会话索引覆盖全部历史，所以不需要 `index:epoch` 判断索引是否完整。读一页历史时，由计数器和游标算出要读的 `seq` 区间，从索引取出全局消息号，再读消息实体；实体缺失（回填的老消息）或索引缺项的 `seq`，从 MySQL 按（会话，`seq`）补齐。`has_more` 只看区间边界：向前翻页看最小 `seq` 是否大于 1，向后翻页看最大 `seq` 是否小于计数器。`index:epoch` 只保留给私聊 feed。
17. **计数器缺失不等于新会话。** 接纳 Lua 发现计数器不存在、但会话索引非空时返回不可用（503），不从 1 重新开始；会话索引也为空才视为新会话。
18. **校准与闸门。** 启动时，在打开监听之前同步完成一次校准：把每个会话的计数器抬到不低于 MySQL 里该会话的最大 `seq`（只抬不降）。运行期由进程内闸门控制：后台每 5 秒读一次 Redis 的 `run_id` 并检查 `seq:ready`，任何 Redis 连接错误也立即触发一次检查；发现变化就关闭闸门、重新校准、再打开。闸门关闭期间，接纳、`focus`、未读和 `read-stats` 返回 503，历史读取照常（缺失的部分从 MySQL 补）。校准需要 MySQL，MySQL 同时不可用时接纳保持 503，直到校准完成。闸门状态同时输出到 `/ops/infra`，`/ready` 仍只检查 MySQL。
19. **AOF 前缀一致，水位不会超过计数器。** AOF 丢尾后的状态是某个时刻的完整前缀，水位只会推进到不超过当时计数器的位置，所以不需要额外的水位回退机制。读取时仍对未读数取 `max(0, ...)`。
20. **回滚 = 恢复切换前的 MySQL 备份 + 清空 Redis 命名空间 + 旧发布包 + 旧版的两个回填命令。** 不做新旧单位的双写，切换之后产生的数据在回滚时丢弃。运维文档写明这一点。
21. **发布脚本支持三段式版本号。** `scripts/build-release.sh` 目前只接受 `vX.Y`，需要接受 `vX.Y.Z`。

## 数据模型

下表的键名省略了命名空间前缀，实际键都带 `Keyspace` 前缀（正式环境 `im:v12:`，验证环境 `im:v13-verify:`），`seq:ready` 也不例外。

### Redis

| 键 | 类型 | 内容 |
| --- | --- | --- |
| `dm:seq:{low}:{high}` | STRING | 私聊会话计数器，当前最大 `seq` |
| `dm:pair:{low}:{high}` | ZSET | 私聊会话索引：成员为全局消息号，分数为 `seq` |
| `group:{G}:seq` | STRING | 群会话计数器 |
| `group:{G}:inbox` | ZSET | 保留：成员为全局消息号，分数改为 `seq` |
| `dm:read:{user}` | HASH | 保留：对方 → 已读 `seq`（单位变化） |
| `group:{G}:read` | ZSET | 保留：成员 → 已读 `seq`（单位变化） |
| `dm:conv-last:{user}` | HASH | 保留，不变 |
| `messages:{id}`、`group-messages:{id}` | HASH | 保留，新增 `seq` 字段 |
| `messages:stream`、`group-messages:stream` | Stream | 事件新增 `seq` 字段 |
| `dm:read:stream`、`group-read:stream` | Stream | 事件字段 `last_read_message_id` 改为 `last_read_seq` |
| `seq:ready` | STRING | 历史回填和编号完成的标记；存在时 Redis 水位已确定是 `seq` |
| `backfill:lock` | STRING | `backfill-seq` 运行期间持有（30 分钟 TTL）；存在时后端拒绝启动、第二次回填拒绝执行 |

- 废弃并删除：`dm:conv:{owner}:{peer}`、`group:{G}:last_accepted_id`、`dm:read:ready`、`group-read:ready`。
- 去重记录（`dedup`、`group-dedup`）不新增字段，重复发送时从消息实体读取 `seq`。
- 除 `backfill:lock` 外，所有新键不设 TTL，容量治理留到 v1.9。

### MySQL

迁移文件仍是一文件一条语句，编号从 023 开始：

- `messages` 新增 `conversation_low_id`、`conversation_high_id`、`seq`（均可空），再加唯一索引（`low`、`high`、`seq`）和索引（`low`、`high`、`server_message_id`，供水位换算查询）；
- `group_messages` 新增可空 `seq`，加唯一索引（`group_id`、`seq`）；
- `conversation_reads` 和 `group_members` 新增 `last_read_seq`（`NOT NULL DEFAULT 0`），旧的 `last_read_message_id` 保留但不再维护；`conversation_reads` 的写入显式把旧列写成 0；
- 迁移只做结构变更。填充 `low`、`high`、`seq` 在 `backfill-seq` 里分批完成，不放进启动时的迁移；
- 新消息写入时由应用同时写入 `low`、`high`、`seq`；
- 异步落库同一（会话，`seq`）对应不同消息时，store 返回专门的冲突错误，消费者记录日志并确认，不重复投递；
- MySQL 回落路径的未读统计只数对方发来的、`seq` 大于 `last_read_seq` 的消息。

## 接纳

私聊和群聊的接纳 Lua 都按下面的顺序：

1. 校验就绪标记 `seq:ready`，缺失返回不可用；
2. 原有的拒绝判断（自己发给自己、幂等命中、正文冲突、非好友或非成员、群已解散、全局号溢出）；
3. 检查会话计数器：不存在且会话索引非空，返回不可用；已达 `MaxSafeSeq`，返回编号溢出。这两项在分配全局消息号之前完成，避免丢弃的请求烧掉编号；
4. 分配全局消息号，再对会话计数器加 1 得到 `seq`；
5. 写入消息实体（含 `seq`）、`dm:pair` 或 `group:{G}:inbox`（分数为 `seq`）、`dm:conv-last`、私聊 feed、幂等记录；
6. 写入 Stream 事件（含 `seq`），返回全局消息号、`seq` 和创建时间。

幂等命中时，返回原消息实体上的 `seq`。接纳结果、HTTP 响应、WebSocket 推送和异步落库都携带 `seq`。

## 历史与热读

- 单会话历史按 `seq` 翻页：不带游标取最新一页；`before_seq` 向前，`after_seq` 向后。方向由查询参数是否存在决定，`after_seq=0` 表示从 `seq` 1 开始向后读，而不是“无游标”。两个游标同时出现返回 400。区间由计数器和游标计算，从会话索引取全局消息号，再读消息实体。
- 实体缺失的 `seq` 或索引缺项的 `seq`，按（会话，`seq`）从 MySQL 补齐。区间内仍然取不到的 `seq`，说明数据在故障中丢失，不返回，客户端按缺口规则处理。
- 私聊 feed 增量同步继续用全局消息号和 `index:epoch`，响应里的消息带 `seq`。
- bootstrap 对每个有游标的群比较会话 `last_seq` 与 `after_seq`，只读取有新消息的群；`after_seq` 为 0 仍表示没有游标。

## 读状态

- `dm:read`、`group:{G}:read` 的值换成 `seq`。推进规则不变：只增不减，Lua 内比较后写入，推进时写 Stream。
- 推进的候选位置不再查消息索引，取 `min(请求的 through, 会话计数器)`；`through` 缺省或为 0 表示推进到计数器当前值。
- 会话列表和 bootstrap：私聊未读 = 会话计数器减去 `dm:read`，群聊未读 = 群计数器减去 `group:{G}:read` 里自己的分数。一次 pipeline 读出 `last_seq`、自己的水位和对方的水位，保证同一快照。会话列表保证 `last_seq >= last_message.seq`（MySQL 的 `MAX(seq)` 作为下限），且空 Redis 窗口不具权威性，总是回落 MySQL 补齐。
- 对方的已读回执：对方的水位大于等于我最后一条消息的 `seq`。
- 群已读人数：对成员水位做 `ZCOUNT`，阈值是该消息的 `seq`。`read-stats` 先按（群，`seq`）在 `group:{G}:inbox` 里取全局消息号，再读实体确认发送者；索引或实体缺失时按（群，`seq`）查 MySQL。
- 入群基线取群计数器的当前值，在 `BeginMutation` 之后读取，顺序与 v1.7 相同；本地无 Redis 模式取 MySQL 的 `MAX(seq)`。
- 启动重建群水位：从 MySQL 的 `last_read_seq` 补齐缺失成员、抬高偏低的位置，只增不降，规则与 v1.7 相同。
- MySQL 异步持久化：`last_read_seq` 用 `GREATEST` 写入。
- `focus` 立即推进到会话计数器当前值。

## 接口

- 消息体（历史、同步、bootstrap、WebSocket 推送、发送响应）增加 `seq`，已接纳消息的 `seq` 一定大于等于 1，只有本地发送中的消息为 0。
- 会话列表：私聊项增加 `last_seq`，`peer_last_read_message_id` 改名为 `peer_last_read_seq`；群项增加 `last_seq`。
- 历史：`before_seq`、`after_seq`、`limit`，响应仍是 `messages` 和 `has_more`。`after_seq` 一旦出现（包括 0）就表示向后读，`seq > after_seq`、由旧到新；与 `before_seq` 互斥。
- bootstrap：群游标字段改为 `after_seq`，私聊 `after_id` 不变。
- `GET /api/groups/:id/read-stats?seq=m`，响应为 `seq`、`message_id`（该 `seq` 对应的全局消息号，供客户端校验）、`read_count`、`member_count`、`all_read`。非成员得到 404 `group_not_found`，成员请求别人的消息得到 403 `not_your_message`，`seq` 对应的消息不存在得到 404 `message_not_found`。
- WebSocket：`focus.ack` 和 `messages.read` 里的位置字段为 `last_read_seq`，消息推送里的消息对象带 `seq`，`group.read` 不变。
- 删除三个旧的 HTTP 已读接口，以及它们的辅助函数、store 方法和测试。
- 计数器未就绪时，接纳和读状态相关接口复用现有的“服务不可用”503 映射。

## 客户端

收到某会话编号为 N 的消息，本地该会话已缓存的最大编号为 M（本地发送中的消息 `seq` 为 0，不参与比较）：

- N = M + 1：追加；
- N > M + 1：存在缺口，按缺失区间 `after_seq=M` 向服务端补拉；
- N <= M 且全局消息号相同：重复，忽略；
- N <= M 且全局消息号不同：服务端回退后编号被重用，删除本地该 `seq` 之后的消息，以服务端为准重新同步尾部；
- 会话列表里的 `last_seq` 小于本地最大编号：服务端回退过，丢弃本地多出的尾部并重新同步；
- 补拉后仍取不到的编号，标记为缺失，不无限重试；
- 本地“已发送”的消息在对账中发现服务端不存在（掉电丢尾）：转成发送失败，正文和原客户端 ID 取自本地缓存的消息记录，用户点击重试时用原客户端 ID 重发。丢尾时服务端的去重记录和消息一起丢失，重发会当作新消息接纳，不会重复。

实现要点：

- IndexedDB 升级版本并清空旧缓存，旧缓存里的全局号游标不能当作 `seq` 使用。消息记录增加 `seq`，并建立（会话，`seq`）索引，支持按 `seq` 删除尾部和查询本地最大 `seq`。缓存读到缺少 `seq` 的旧记录时视为无效。
- 全局消息号仍是跨会话比较活跃度的依据（缓存淘汰排序），`seq` 只在会话内比较。
- 会话预览（最后一条消息）只在新消息的 `seq` 更大时才覆盖，避免乱序或重复推送让预览回退。
- 本地未读：新消息 N = M + 1 时加 1，重复和旧编号不计，出现缺口时重新拉取会话列表，以服务端为准。
- 打开会话时本地先把未读清零，随后以 `focus.ack` 里的 `last_read_seq` 为准。
- 已读回执比较 `message.seq` 与 `peer_last_read_seq`，不再比较全局号。
- `read-stats` 的响应带 `message_id`，与本地该 `seq` 对应消息的全局号不一致时丢弃，防止编号被重用后显示别的消息的人数。

## 历史回填与切换

`backfill-seq` 是一次性命令，幂等，停后端后执行，顺序与 v1.7 相同：备份 → 确认持久化队列已排空 → 停后端 → 替换文件 → 回填 → 启动。命令（以及 `--verify` 形式）先执行迁移，再依次：

1. **前置检查。** 对每个私聊方向和每个群，比较 Redis 里旧索引（`dm:conv`、`group:{G}:inbox`）的条数与 MySQL 的条数。Redis 条数更多说明有已接纳但未落库的消息，终止并提示先排空队列。
2. **填充 MySQL。** 分批填写 `conversation_low_id`、`conversation_high_id`；再按会话、按全局消息号顺序分批编号 `seq`（私聊、群聊），已有 `seq` 的行不动，新编号接在该会话已有最大值之后。解散的群同样处理。
3. **重建 Redis。** 分批建立 `dm:pair`；用 `seq` 重写 `group:{G}:inbox`；设置 `dm:seq`、`group:{G}:seq`（取当前值与 MySQL 最大 `seq` 中较大者，不降低）；只对已存在的消息实体补写 `seq`，不创建空实体；删除 `dm:conv:*` 和 `group:{G}:last_accepted_id`；删除旧的读事件 Stream。
4. **换算水位。** 对每个私聊水位和群水位，取 Redis 当前值与 MySQL 旧列中较大者作为全局消息号，换算成“该会话内全局号不大于它的最后一条消息的 `seq`”，没有对应消息则为 0。结果写入 Redis 和 MySQL 的 `last_read_seq`。私聊水位的换算要包含双方的消息，因为发送者的水位会推进到自己发出的消息。

   换算水位时，只有 `seq:ready` 能证明 Redis 水位已经是 `seq`。`seq:ready` 不存在时（首次回填、失败后重跑），所有 Redis 水位都按旧全局消息号换算；崩溃窗口内已经换算过的值再换算只会变低（未读偏多），是安全方向。`seq:ready` 存在时（重跑或切换后恢复），Redis 水位按 `seq` 保留并截断到会话计数器。MySQL 的 `last_read_seq` 始终是下限，换算结果不会低于它。只存在于 Redis 的水位也要扫描 `dm:read:*` 和 `group:*:read` 换算，不能只按 MySQL 行处理。
5. **校验。** 每个会话的消息条数等于最大 `seq`，没有 `seq` 为空的行；每个水位不大于对应计数器；索引条数等于 MySQL 条数。
6. **写入 `seq:ready`。** 通过后写入，并记录 Redis 内存变化。失败时不写 `seq:ready`，重跑会按第 4 步重新换算未完成的水位。

回填开始前持有 Redis 的 `backfill:lock`（30 分钟 TTL，带 token 的释放），运行中的后端和第二个回填都会拒绝启动或执行。回填命令不依赖后端在运行。空数据库也要运行一次，用来写入 `seq:ready`。

## 失败与降级

| 场景 | 行为 |
| --- | --- |
| Redis 不可用 | 接纳、已读、未读相关接口失败，不回落 MySQL，与 v1.6、v1.7 一致 |
| MySQL 不可用 | 编号分配、未读、已读照常，异步落库积压重试；此时若 Redis 重启，校准无法完成，接纳保持 503 |
| 计数器落后于 MySQL（丢 AOF 尾部） | 启动或发现 Redis 重启后校准，校准完成前接纳和读状态返回 503 |
| 计数器缺失但会话索引非空 | 该会话接纳返回 503，等待下一次校准 |
| `seq:ready` 丢失 | 接纳和读状态返回 503，重新回填后恢复 |
| 落库遇到（会话，`seq`）冲突 | 记录错误日志并确认，不覆盖；客户端按对账规则恢复 |
| 掉电丢 AOF 尾部（约 1 秒内） | 已确认的消息可能丢失；客户端发现后以服务端为准重新同步，自己发的消息转成发送失败，可用原客户端 ID 重发 |

## 实现中确定的细节

这些不需要产品决策，实现时按原则处理，结果记入实现进展。

1. 校准在会话数很多时要控制批大小和启动耗时；Redis 重启后的校准复用同一段逻辑，需要的 MySQL 查询按会话分页。
2. MySQL 回填编号要分批，避免长事务；唯一索引在回填前就存在，可空 `seq` 不会冲突。
3. 删除旧 HTTP 已读接口后，相关 Go 测试、smoke 用例和文档要同步清理（前端源码本身没有调用）。
4. 检测 Redis 重启的 `run_id` 通过 `INFO server` 读取，由新的监视组件负责，不复用基础设施管理器的 ping 循环。
5. 恢复测试：`infractl redis-restart` 保留数据目录，不会制造“计数器落后”。验证时先在验证命名空间手工把计数器改小，再触发校准；验证实例和正式实例共用同一个 Redis 容器，重启容器会影响正式实例，需要单独确认后再做。
6. 丢包和缺口的浏览器测试通过 smoke 注入的 WebSocket 包装层合成缺号帧，不依赖真实丢包。
7. 清理脚本需要新增 `dm:seq`、`dm:pair`、`group:{G}:seq` 的清理，私聊键用内部用户 ID，清理时由 MySQL 先查出账号对应的 ID。

## 验收方向

1. 每个会话的 `seq` 从 1 开始连续，发送 N 条后最大 `seq` 为 N；重复发送返回同一个 `seq`。
2. 同一会话并发发送，`seq` 无重复、无空洞。
3. 私聊两个方向的消息在同一个会话里按 `seq` 排序；删除好友再加回来后继续编号。
4. 会话列表的私聊和群聊未读逐项正确，且与切换前一致；`last_seq`、`peer_last_read_seq` 正确。
5. 异步落库窗口内，未读、已读和历史仍然正确，落库后不变化。
6. 模拟丢一条推送：客户端收到跳号后自动补拉，界面不缺消息。
7. 模拟服务端回退（计数器变小）：客户端发现后以服务端为准重新同步。
8. 计数器被改小后触发校准：计数器被抬回，新消息不撞号；校准期间接纳返回 503。
9. 回填后每个会话的消息条数等于最大 `seq`，已读位置换算正确；缺少 `seq:ready` 时后端拒绝启动。
10. v1.7 行为不变：隐式已读、群回执、私聊回执、成员管理。
11. 掉电丢尾后，客户端把本地多出的已发送消息转成发送失败，点击重试用原客户端 ID 重发成功，且不重复。
12. 旧的三个 HTTP 已读接口返回 404 或 405（路由已删除；路径仍存在其他方法时 Gin 返回 405）；浏览器在前台持续收消息时不发送任何已读 HTTP 请求。

## 不在本版范围

- 跨实例广播和单会话替换（后续子版本）；
- 可靠投递、pending 接管、死信和对账程序（后续子版本）；
- TTL 和容量治理（v1.9）；
- 消息实体改按（会话，`seq`）存键、彻底去掉会话索引：等 v1.9 有内存实测数据再决定；
- 已解散群的计数器与索引清理、账号删除后的 `dm:seq`、`dm:pair` 清理（v1.9）。

## 风险

1. **改动面大。** 涉及消息模型、读模型、接口、前端缓存和回填切换，需要分步实现和完整回归。
2. **已读位置换算。** 回填时把全局消息号换算成 `seq`，换算错误会让未读数偏差，必须校验。
3. **掉电丢尾窗口仍然存在。** 靠校准和客户端对账缓解，不能消除，见 v1.8 总览。
4. **私聊未读短暂偏大。** 发送者水位异步推进期间，自己的消息可能被算成未读。
5. **回滚成本。** 回滚会丢弃切换之后产生的数据，需要恢复备份并重建 Redis。
6. **新键没有 TTL。** 计数器和会话索引随会话数增长，容量治理留到 v1.9。
7. **无 Redis 本地模式不支持已读。** 本地开发时未读数不会清零。
