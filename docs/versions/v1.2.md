# v1.2 私聊消息链路

状态：开发中，基础链路已验证（2026-10-25）。

## 目标

在不提前实现私聊已读和高可用治理的前提下，搭建私聊消息从客户端发送、Redis 原子接纳、实时通知、异步投递到 MySQL 持久化的完整基础链路。

本版按单 Redis、单 RabbitMQ、单后端实例和基础消费者运行，先验证正常消息路径、基本幂等和现有私聊行为兼容。完整的 Redis 消息读取链路与读取优化留到 v1.6；Redis/RabbitMQ 的高可用、故障转移、跨组件补偿与一致性治理留到 v1.7；容量验证与调优留到 v1.8。

## 讨论结论

以下内容已确认，并作为本版实施约束：

- 客户端每次发送消息都携带浏览器生成的 UUID `client_message_id`，用于客户端重试去重；同一条消息的重试必须保持原值。
- 服务端在 Redis Lua 脚本中使用原子 `INCR` 分配 `server_message_id`，保持 `uint64` 类型，用于服务端排序、拉取和异步链路去重。时间戳和发送者 ID 作为消息字段保存，不编码进服务端消息号。
- Redis Lua 脚本原子完成好友关系判断、客户端消息号去重、服务端消息号分配、消息及收发箱写入和 Redis Stream 写入。
- Lua 执行成功表示消息已经被 Redis 消息链路接纳，不表示 MySQL 已经完成持久化。
- 在线通知使用 WebSocket；WebSocket 是实时通知渠道，不作为可靠持久化或最终送达依据。
- Redis Stream 将消息投递到 RabbitMQ，RabbitMQ 异步驱动 MySQL 落库。
- MySQL 使用服务端消息号和客户端消息号进行幂等保存，重复投递不能产生重复消息。
- 消息读取需要同时覆盖 Redis 中尚未落库的热数据和 MySQL 中已经持久化的历史数据，并按服务端消息号合并、去重和排序。
- 本版保持现有私聊接口、消息格式、好友权限、文本限制、WebSocket 基本行为和历史分页行为；不主动改变用户可见的聊天操作方式。

## 基础运行前提

v1.2 只建立基础链路，不承担完整高可用能力：

- 单 Redis 实例；
- 单 RabbitMQ 实例；
- 单后端实例；
- 基础 Stream 消费者和 RabbitMQ 落库消费者；
- 不配置 Redis/RabbitMQ 集群、主从切换和跨实例路由；
- 不做压力测试、容量调优和高可用故障演练。

在这个前提下，本版需要保证正常路径和基本重复请求不会产生重复消息；进程崩溃、组件故障转移和跨组件自动修复属于后续治理范围。

## 消息链路

### 1. 客户端发送

客户端向现有私聊发送接口提交正文和 `client_message_id`。服务端完成登录、参数、好友关系和消息正文校验后，将请求交给 Redis 消息接纳脚本。

客户端消息号只用于识别同一发送请求的重试，不能作为服务端排序号。相同发送者重复提交同一个客户端消息号时，应返回第一次接纳的消息结果；同一个客户端消息号对应不同正文时，应返回冲突错误。

### 2. Redis Lua 原子接纳

Lua 脚本在 Redis 内一次完成以下操作：

1. 根据 Redis 中的好友关系投影判断双方是否允许发送；
2. 查找 `(sender_id, client_message_id)` 对应的去重记录；
3. 如果已经接纳，返回原消息的服务端消息号和结果；
4. 如果是新消息，分配 `server_message_id`；
5. 写入消息实体；
6. 把消息 ID 写入发送方寄件箱；
7. 把消息 ID 写入接收方收件箱；
8. 把待落库事件写入 Redis Stream；
9. 返回 `accepted` 结果及消息信息。

消息实体保存完整消息内容，收件箱、寄件箱和 Stream 以消息 ID 或轻量事件为主，避免重复保存大段正文。具体 Redis key、列表或有序结构、保留数量和过期规则在详细设计时确定。

Lua 脚本依赖 Redis 中的好友关系投影。好友接受和删除等已有好友操作需要同步维护该投影；本版不重做好友体系，只补齐私聊消息链路所需的数据同步。

### 3. HTTP 响应

本版区分两个服务端状态：

```text
accepted   消息已经进入 Redis 主链路
persisted  消息已经提交 MySQL
```

发送接口在 Redis Lua 返回 `accepted` 或已知的 `duplicate` 后即可返回，不等待 RabbitMQ 消费和 MySQL 提交。前端可以继续使用现有的发送中、发送成功和失败重试体验；接口和版本文档中必须明确“发送成功”的内部含义已经是消息被链路接纳。

### 4. WebSocket 通知

Redis Lua 成功后，后端向在线聊天连接尽力推送消息事件：

- 在线接收方收到实时消息；
- 发送方当前连接按现有行为收到必要事件；
- 推送失败不回滚 Redis 中已经接纳的消息；
- 客户端根据服务端消息号去重；
- 断线或漏收时通过历史/补收接口获取消息。

WebSocket 推送不代表消息已经写入 MySQL，也不代表客户端一定已经完成处理。

### 5. Redis Stream 投递 RabbitMQ

基础 Stream 消费者读取待落库事件，发布到 RabbitMQ，并等待 RabbitMQ publisher confirm。v1.2 的基础路径按以下规则运行：

```text
读取 Stream → 发布 RabbitMQ → publisher confirm → 确认并清理 Stream 事件
```

RabbitMQ 的 consumer ack 与 publisher confirm 分开处理。publisher confirm 表示消息进入 RabbitMQ，不表示 MySQL 已提交；RabbitMQ 落库消费者只有在 MySQL 事务成功后才发送 consumer ack。

本版暂不完整处理 Stream pending 接管、跨组件重放、死信、消息确认水位和按 MySQL 提交结果清理 Stream。该部分作为已知限制记录，v1.7 再进行可用性强化。

### 6. RabbitMQ 异步落库

RabbitMQ 消费者接收消息后，在 MySQL 中执行幂等事务：

- 以 `server_message_id` 防止 Stream 或 RabbitMQ 重复投递造成重复行；
- 以 `(sender_id, client_message_id)` 保持客户端重试幂等；
- 首次消费插入消息；
- 重复消费识别为已完成并正常 ack；
- MySQL 提交成功后才发送 RabbitMQ consumer ack。

历史读取按 `server_message_id` 排序，不要求异步消费者必须严格按照服务端消息号顺序到达 MySQL。

### 7. 基础读取保障

v1.2 不完整实现 Redis 读链路和读取性能优化，但必须保证刚被 Redis 接纳、尚未完成 MySQL 落库的消息不会因为异步窗口而完全不可见：

- HTTP 发送响应返回完整消息；
- WebSocket 事件携带完整消息或服务端消息号；
- 必要时可以从 Redis 读取尚未落库的消息；
- 已有历史消息继续通过现有历史接口读取；
- 客户端按服务端消息号去重，避免 WebSocket、Redis 和 MySQL 数据重复显示。

完整的 Redis 收件箱、寄件箱读取模型、热数据范围、Redis/MySQL 合并、会话列表优化、分页游标优化和读请求降 MySQL 统一放到 v1.6 讨论和实现。v1.2 不要求解决 Redis 丢失、历史重建和多实例游标一致性。

## 与私聊已读的边界

私聊已读属于 v1.3，本版不新增或重做以下内容：

- Redis 已读位置；
- 已读位置推进接口；
- `messages.read` 事件；
- 发送方已读状态；
- 私聊未读数量的 Redis 化；
- 已读位置与消息游标的一致性治理。

v1.2 需要保持现有私聊接口和页面行为可用。由于消息先进入 Redis、再异步写入 MySQL，现有未读统计在消息尚未落库的短时间内可能存在延迟；未读和已读的统一迁移在 v1.3 处理。

## 建议验收方向

1. 好友发送新消息时，客户端消息号、服务端消息号、Redis 收发箱和 Stream 记录正确。
2. 同一个客户端消息号重复提交不会生成第二条消息，并返回原消息结果。
3. 非好友、自己给自己发送和非法消息请求在 Redis 接纳前被拒绝。
4. 在线接收方可以通过 WebSocket 收到消息，重复事件不会在页面显示重复消息。
5. RabbitMQ 消费成功后消息能够幂等写入 MySQL，重复投递不会产生重复行。
6. 消息尚未完成 MySQL 落库时，发送响应、WebSocket 或最低读取保障仍能让客户端获得已接纳消息；客户端不会因为重复通知显示两条相同消息。
7. 接收方离线时消息保留，重新打开会话或按游标拉取可以获取消息。
8. 现有私聊接口、历史分页、好友权限和前端基本聊天体验继续可用。
9. 本版不以 Redis/RabbitMQ 故障转移、跨组件自动修复或压力指标作为验收条件。
