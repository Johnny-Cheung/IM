# v1.9 容量验证与调优

状态：代码优化完成，待真实链路验证与压测（2026-11-02）。relay 流水线投递、consumer 单 worker 批量落库、发送路径缓存和客户端已读游标已实现并通过后端/前端单元测试与 race 检查；尚未在真实 MySQL/RabbitMQ 环境执行完整压测，也未切换正式 `8198`。删除 `dm:feed`/`index:epoch` 的读模型结构变更和按会话懒加载留给 [v1.10](v1.10.md)，本版范围不变。

## 目标

在不改变 HTTP/WS 入口、读模型和数据库结构的前提下，先解决压测已经确认的异步链路瓶颈，并把同步发送路径上的 MySQL 查询收敛到缓存：

- relay 从 Redis Stream 批量读取，流水线发布并收集 RabbitMQ publisher confirm，整批确认成功后批量确认 Stream；
- consumer 每个队列保留一个 worker，攒批写入 MySQL，成功提交后才 ack；
- direct 和 group 两条链路同步改造；
- 发送鉴权使用进程内 session 缓存，username 解析使用进程内用户缓存，群成员广播优先使用 Redis；
- 保持现有至少一次投递、幂等、冲突分类、死信和 `queue_drain` 语义。

目标是在真实环境中把异步持久化从压测基线的约 `198/s` 提升到接近接纳能力的量级，并让 `201` 之前的稳态发送路径不再查询 MySQL；具体数字以真实压测结果为准，不把微基准当作验收结论。

## 背景

2026-11 的压测记录在 [bench/README](../../bench/README.md)：

| 项目 | 结果 |
| --- | --- |
| WebSocket 长连接 | 20 万连接，约 6 GB 内存、2.4 核，0 失败 |
| 同步接纳 | 10 连接 9,319 QPS，P99 2.12 ms |
| relay | 逐条发布并等待确认，约 386/s |
| consumer | `Qos(1)` + 每条一个 MySQL 事务，约 198/s |
| 端到端 | 同步接纳与异步落库相差约 47 倍；10 秒可积压 82,380 条 |
| 一致性 | 100,507 条接纳最终落库 100,507 行，`seq` 无空洞、死信 0 |

根因是 relay 和 consumer 都在单条等待 IO：relay 每条持久化消息等一次 broker 确认，consumer 每条消息一个事务和一次 commit。批量和并发是两个独立维度；本版先实现批量化，consumer 暂不增加多 worker。

## 已完成

### relay

- direct/group relay 的 `XReadGroup` 批量大小改为 100，`drainPending` 使用同一批量路径。
- `relayPublisher` 改为返回确认 receipt；AMQP 实现使用 `PublishWithDeferredConfirmWithContext`，整批消息连续发布后才逐个等待确认。
- 移除了 `NotifyPublish` 单条确认模型，避免确认通道缓冲只有 1 时阻塞 RabbitMQ 读取协程。
- 全部确认成功后，用一个 Lua 脚本批量 `XACK + XDEL`；脚本内部使用可变参数 `XACK`/`XDEL`，一批最多 100 个 ID，内部调用从每批 2N 次降为 2 次。任何发布错误、nack、确认通道关闭或 30 秒确认超时都整批不 ack，保留 pending 等待重投，不做部分 ack。
- malformed entry 与正常 entry 同批处理：malformed 只删除，不发布；`Relayed`/`Recovered` 仍按消息条数累计。

### consumer

- direct/group consumer 改为每个队列一个 worker，`Qos(100)`，最多 100 条或 10 ms 攒批。
- 增加可选 `MessageBatchPersister` / `GroupMessageBatchPersister`；只实现单条接口的 persister 继续走旧路径。
- store 增加 `PersistMessages` / `PersistGroupMessages`：一个事务、多行 `INSERT ... ON DUPLICATE KEY UPDATE id = id`。
- 只有 `RowsAffected == len(messages)` 才 commit；任何重复、冲突或参数异常都回滚并返回 `ErrBatchFallback`，由现有逐条 `PersistMessage` / `PersistGroupMessage` 完成三重幂等与冲突判断。
- transient 错误整批退避重试；message/conflict 错误或批次回落逐条处理，毒消息按原有规则进入死信。
- 事务提交成功后才 ack；malformed 单独死信；取消或连接关闭时不 ack，已收 delivery 都会结束 in-flight 计数。

### 安全保护

- `store.Open` 解析 DSN 并拒绝 `clientFoundRows=true`。单条和批量写入都用 `RowsAffected` 判断重复；开启 `clientFoundRows` 会把未变化的重复行算成 1，可能掩盖 `seq`/客户端幂等键冲突。
- 真实 MySQL 集成测试增加了批量全插入、重复回落、冲突回落和回滚后无部分写入的用例；默认跳过，尚未执行。

### 发送路径缓存

完整消息链路下，消息本身本来就只写 Redis；本轮把 `201` 之前的鉴权和身份查询也移出 MySQL：

- `requireUser` 增加进程内 session 缓存。命中时不再执行 `sessions JOIN users`；未命中才回源 MySQL，并只缓存未撤销、未过期的会话。
- session 缓存按用户维护 mutation sequence。登录/顶号、退出、改密、改昵称都会递增该用户的 sequence，并让该用户的缓存项失效；缓存回填会记录查询前观察到的 sequence，如果查询期间发生 mutation 就不落缓存，避免把旧会话重新写回。
- session 缓存 TTL 为 5 分钟，作为绕过 API 的外部撤销的兜底；正常撤销走显式 mutation。
- 登录成功后直接写入新 session 缓存，避免登录后的第一条消息回源 MySQL。
- `findUser` 增加 username → public profile 的进程内缓存。用户名不可变，注册/登录回填，改昵称时按 key 失效；缓存未命中回源 MySQL。用户缓存 TTL 为 1 小时。
- 群消息广播名单改为优先读取 Redis `group:{G}:members`（群消息接纳 Lua 已经依赖该集合），Redis 不可用或为空时才回源 MySQL，并使用脱离请求取消的提交上下文，避免客户端断开导致已接纳消息不广播。
- 缓存不改变消息接纳、幂等、`seq`、Stream 和异步持久化逻辑；`201` 仍只表示 Redis 接纳。

### accept.lua 与 relay 微优化（2026-11-02）

- `accept.lua` 和 `group_accept.lua` 的全局消息 ID 分配从“先 `GET`、必要时 `SET` 到 seed floor、再 `INCR`”改为“直接 `INCR`，结果不高于 seed floor 时再纠正并 `SET`”。正常路径少一次 `GET`；`EXISTS message_key`、seq 检查和所有读模型写入保持不变。
- `ack_delete.lua` 的批量 `XACK + XDEL` 从逐条循环改为可变参数命令；仍然是同一个原子 Lua，每批最多 100 个 ID，内部调用从 2N 降为 2。
- 本轮不改 dedup 格式、不改 Stream 内容、不改 `implicitRead` 的合并与冲刷机制、不改 `201` 语义；redis Stream 仍是 Redis 侧的 outbox。窗口与队列容量调参见下一节。
- 新增低计数器（低于 seed floor）的直接/群聊接纳测试，验证 ID 抬升和后续自增。

### implicitRead 窗口与队列容量（2026-11-02）

- 合并窗口从 `100ms` 提高到 `1s`，每个会话在同一窗口内的多条消息只推进一次水位线；已读回执本身对秒级延迟不敏感。
- `implicitReadMaxPending` 从 `256` 提高到 `4000`，与更长的窗口配套，降低高并发会话下因队列满而丢弃批次的概率。
- 丢弃仍然只是“这次不推进水位线”，不会写错位置；同一会话后续消息会以更大的 `throughSeq` 覆盖前进。若该会话再无新消息，水位线会停留在旧值，这是既有队列满语义，不因本次调参改变。
- flush 仍是单个 goroutine 顺序处理，`maxPending` 是排队容量而不是并发度；窗口变长后单次 flush 的批次数会更多，`implicitReadDrainTimeout=5s` 和 `implicitReadMaxRetries=3` 保持不变。
- 本轮只改两个常量，不改已读模型、Redis 键或接口语义。

### 客户端已读游标（2026-11-02）

服务端不再根据“消息已投递 + 用户聚焦”推断接收者已读；改为客户端把实际渲染到视口内的最大 `seq` 通过 WebSocket `read` 帧上报，服务端只做校验、clamp 和 max 写入。

- 协议：`{"type":"read","kind":"direct","username":"bob","last_read_seq":42}` 或 `{"type":"read","kind":"group","group_id":9,"last_read_seq":128}`。目标必须与当前 focus 一致，`last_read_seq=0` 被忽略（`AdvanceRead` 的 0 表示“推进到会话最新”）。
- 服务端复用现有 `AdvanceRead`：clamp 到会话计数器、只增不减、仅在真正前进时写 `dm:read`/`group:{G}:read` 和 read stream；直聊 `Advanced` 时广播 `messages.read`，群聊通过 `publishGroupReadFromRedis` 广播 `group.read` 并排除 reader。没有新增 `read.ack`。
- `focus` 语义不变：打开会话仍推进到最新，`focus.ack` 继续返回 `last_read_seq`。因此“进入即已读、后台不自动已读”保持不变；停留前台期间滚到历史位置时，新消息不再自动已读。
- 删除消息驱动的接收者/群成员推进：`implicit_read.go` 只保留发送者自读；删除 `focusedGroupUsers` 的全量在线连接扫描、`AdvanceReadMany` 的 httpapi 调用和群聊 `memberIDs` 广播参数。发送者自读仍用 1s 窗口，因为放慢会让发送者切走后短暂看到自己的消息未读。
- 前端在消息渲染后按 DOM 几何测量可见行（`.message-row[data-seq]` 与滚动容器相交的最大 `seq`），约 1 秒尾随上报；会话切换、标签页隐藏、`pagehide`、卸载和重连时 flush。隐藏时先发 `read` 再发 `blur`；只有收到当前目标的 `focus.ack` 后才允许发送 `read`，避免切换时 `read` 早于 `focus` 被忽略。
- `readingNow` 增加“接近底部”条件：滚到历史位置时新消息不再清零本地未读；滚回底部后由 read 游标推进并在本地收敛。
- 限制：重连/重新可见仍会通过 `focus` 推进到最新；没有 ack，发送成功不代表 Redis 已写入，依靠单调水位和下一次刷新校准；旧前端不发送 `read` 帧时，持续聚焦期间的新消息不会自动已读；群聊每个活跃 reader 每秒最多一条 `group.read`，大群扇出需要压测观察；水位只增不减，seq 回滚/复用时沿用现有 resync 语义。
- 测试：新增 WS read 帧的 direct/group、目标不匹配、零 seq、非前进、terminal error、隐式只推进发送者等后端测试；新增前端 `readCursor.test.ts` 覆盖帧生成、可见性几何、节流合并、切换 flush、失败保留和重连重放。

### 测试修复

- race 检查发现 `implicitRead.flushDue` 在加锁前读取 `pending` 长度；已把容量读取移入锁内，避免与并发 `enqueue` 写 map 形成数据竞争。该问题与缓存逻辑无关，是新增测试调度暴露的既有竞态。

## 语义与限制

- 投递语义仍是至少一次；确认后、批量 ack 前崩溃会产生重复投递，consumer 依靠现有幂等键吸收。
- `201` 仍表示 Redis 接纳，不代表 MySQL 已落库；Redis AOF `everysec` 的掉电丢尾窗口不变。
- relay 仍使用 `mandatory=false`，没有新增未路由 return 处理；队列拓扑依赖 relay 启动声明和现有运维约束。
- relay 的毒消息仍可能阻塞整批；本轮只增加确认超时，没有引入 delivery-count 隔离。
- consumer 暂为单 worker 批量，不保留跨 worker 的并发写入；同会话落库顺序仍由单 worker 保持。
- 批次内只要出现重复/冲突就回滚并回落逐条，恢复场景会变慢，但不会静默 ack 冲突。
- session/user 缓存是进程内缓存，只适用于当前单实例部署：多实例之间不会互相失效，届时应改为 Redis 共享缓存或共享撤销版本。
- 缓存未命中、进程重启后第一次访问仍会回源 MySQL；这里的目标是稳态消息请求不查 MySQL，不是所有冷启动请求都不查。
- session 缓存 TTL 为 5 分钟，外部直接修改 MySQL 的撤销最多需要该窗口生效；正常登出、改密、顶号走进程内 mutation，立即失效。

### 真实链路压测（2026-11-02，Ubuntu 本机 + 容器化 MySQL/Redis/RabbitMQ）

已完成 direct 链路的端到端压测，完整数据与测量方法见 [bench/README](../../bench/README.md)：

- **异步链路批量改造有效**：改造前 consumer 约 198/s、relay 约 386/s；改造后压测产生的积压在压测结束时就已排空（改造前 8 万条积压需约 4 分钟），实测排空速率约 12,000–14,800/s。
- **端到端一致性**：多轮累计接纳与 MySQL 落库行数精确吻合，会话 `seq` 零空洞，死信 0。**零丢失、零重复。**
- **发送路径缓存有效**：10 连接 8,045 → 12,423 QPS（+54%），P50 1.14ms → 0.64ms。
- **`implicitRead` 容量修复有效**：改前累计丢弃 51 万次以上，改后（窗口 1s、上限 4000）复测丢弃 0 次。
- **接纳上限**：约 15,000–16,600 QPS，由 Redis 单线程的命令吞吐决定（压测中 Redis 打满、其他依赖远未饱和），与连接数基本无关。
- **`accept.lua` 微优化**：命令从 23 条降到 20 条（静态统计），实测口径约 16 条/消息，QPS 提升约 3–7%。

**压测发现的新问题（尚未修复）**：长时间高负载下 **consumer 被批量回落拖垮**。`messages.go` 的 `RowsAffected != len` 会让整批回滚，`rabbit_consumer.go` 随即把整批 100 条降级为逐条路径（慢约 42 倍）；`Qos(100)` 下一次预取里只要一条重复，整批都走慢路径，并随积压自我强化。实测积压 196 万条、consumer 掉到 141–343 行/秒。排查确认重复来自 relay 的至少一次投递重投（MySQL 无重复行、retries 与死信均为 0），**数据没丢没重**——问题在于用整批降级应对一条重复。修复方向与风险提示见 bench 文档，未在本版实施。

## 不在本版

- HTTP/WS 发送入口重构；
- 读模型的结构性重写（Redis 键和 MySQL 表保持不变）；已读只增加客户端 `read` 游标并调整 `implicitRead` 容量，不改存储模型；删除 `dm:feed`/`index:epoch` 的结构变更移至 [v1.10](v1.10.md)；
- 多 worker 并发落库；
- RabbitMQ 拓扑、数据库迁移、多实例或高可用；
- 正式 `8198` 切换。
