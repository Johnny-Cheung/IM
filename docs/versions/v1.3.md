# v1.3 群聊消息链路

状态：开发中，基础实现已完成，隔离环境验证待完成（2026-10-25）。

## 目标

在 v1.2 私聊消息链路的基础上，建立群聊消息从客户端发送、Redis 原子接纳、在线通知、异步投递到 MySQL 持久化的基础链路。群聊与私聊共享消息基础设施和确认语义，但分别实现业务处理器、Redis 接纳脚本、消息表和 WebSocket 接收者选择。

本版只完成群聊消息链路，不实现群聊已读。私聊和群聊的完整 Redis 读取链路统一留到 v1.4；私聊已读留到 v1.5；群聊已读留到 v1.6；可靠性与一致性治理留到 v1.7；容量验证、压力测试和调优留到 v1.8。

## 讨论结论

以下内容作为 v1.3 的实施边界：

- 客户端消息号继续使用浏览器生成的 UUID；同一条消息重试时复用原 `client_message_id`。
- 群聊和私聊采用相同的服务端消息号生成规则、消息号安全范围和 accepted/persisted 语义。
- 私聊和群聊消息分别写入 `messages` 与 `group_messages`，不合并为一张带大量可空字段的消息表，也不为群成员复制多份消息行。
- 群聊在 Redis 中使用每个群一份统一信箱；消息只写入群信箱，不写入每个成员的个人收件箱和寄件箱。
- Redis Lua 单独实现群聊接纳脚本，负责群成员权限判断、群聊幂等、服务端消息号分配、群消息实体、群信箱和群 Stream 写入。
- 在线群成员通过 WebSocket 尽力接收完整群消息事件；推送失败不回滚 Redis 接纳结果。
- Redis Stream、RabbitMQ exchange、queue、routing key 和 consumer group 使用群聊独立命名空间；群事件不能混入 v1.2 私聊队列。
- MySQL 仍然是群成员关系和历史访问权限的权威来源，Redis 群成员投影只用于消息接纳和在线投递辅助。
- v1.2 的私聊链路继续保持可用；群聊启用新链路后，未配置 Redis/RabbitMQ 时继续使用现有 MySQL 直写路径。

## 运行前提和范围边界

v1.3 继续按单 Redis、单 RabbitMQ、单后端和基础消费者运行：

- 不配置 Redis/RabbitMQ 集群、主从切换和多实例路由；
- 不实现 Stream pending 接管、死信、复杂重放和跨组件补偿；
- 不实现群聊已读位置、群成员逐条已读回执和 `group.messages.read`；
- 不实现完整私聊/群聊 Redis 读取模型、会话列表 Redis 化和读取性能调优；
- 不做 100 人群消息 fanout 压力测试、容量验证和最终性能指标；
- 不增加群公告、系统消息、@提醒、撤回、搜索、转发等消息类型；
- 不改变现有群成员管理、群主权限、100 人上限、入群历史、踢出、退群和解散行为。

v1.3 必须补齐群消息异步窗口的最低可见性保障。刚被 Redis 接纳但尚未落库的群消息，发送响应和 WebSocket 事件要携带完整消息；群历史最新页、`before_id` 和 `after_id` 需要能够从 Redis 热数据与 MySQL 结果合并读取。完整的读取模型和读请求降 MySQL 留给 v1.4。

## 消息模型和消息号

### 两张业务消息表

私聊和群聊继续分别存储：

```text
messages        私聊消息
 group_messages 群聊消息
```

`group_messages` 保留 MySQL 自增 `id` 作为内部主键，并新增与私聊一致语义的 `server_message_id` 对外消息号。应用层 `store.GroupMessage.ID` 改为读取 `server_message_id`，历史、分页、WebSocket 和前端 `id` 继续使用对外消息号。

群消息需要保留以下字段：

- `server_message_id`；
- `group_id`；
- `sender_id`；
- `client_message_id`；
- `body`；
- `created_at`。

群消息幂等范围为：

```text
sender_id + group_id + client_message_id
```

私聊继续使用：

```text
sender_id + recipient_id + client_message_id
```

### 服务端消息号

群聊和私聊共用 Redis `INCR` 的生成规则和 `MaxSafeMessageID` 上限。v1.3 需要将启动时的消息号水位扩展为同时考虑 `messages.server_message_id` 和 `group_messages.server_message_id`；未配置 Redis 时的 MySQL 直写路径也必须使用同一套序列分配规则，不能重新使用 `LastInsertId` 作为对外消息号。

旧群消息迁移时以原有 `group_messages.id` 回填 `server_message_id`，保持已有群历史游标和已读位置兼容。私聊与群聊的读取游标始终绑定各自会话或群，不把不同消息域的 ID 直接进行业务比较。新消息使用统一的 Redis 分配器，启动水位会同时避开两张表中已有的最大消息号；旧数据不额外承诺跨表全局唯一。

该决定意味着：

- 不重映射已有群消息的对外 ID；
- 不修改旧群成员的历史游标数值；
- 不依赖 MySQL 两张表之间无法直接建立的跨表唯一索引；
- v1.4 读取层按会话或群分别处理游标。

## Redis 群聊数据模型

群聊使用独立于 v1.2 私聊的 key 和队列命名空间。具体前缀和部署注入方式在实现步骤中确定，至少需要区分正式 `8198` 和验证 `8199`。

建议的逻辑数据包括：

```text
群成员投影       group:{group_id}:members
群解散标记       group:{group_id}:dissolved
群消息实体       group-messages:{server_message_id}
群消息去重       group-dedup:{group_id}:{sender_id}:{client_message_id}
群统一信箱       group:{group_id}:inbox
群接纳水位       group:{group_id}:last_accepted_id
群待落库 Stream   group-messages:stream
```

群统一信箱使用消息号有序结构保存消息索引，保留数量和实体 TTL 沿用 v1.2 的轻量策略；具体容量参数记录在实现文档和部署配置中，96 MiB Redis 下的容量风险留给 v1.8 验证。

群成员投影必须覆盖：

- 建群；
- 邀请成员；
- 踢出成员；
- 成员主动退群；
- 群主退出导致的解散；
- 服务启动时从 MySQL 全量重建；
- 群解散后的发送和读取拒绝。

移除成员和解散群的投影更新必须采用 fail-closed 处理，不能出现 MySQL 已经拒绝成员但 Redis 仍允许发送的静默窗口。投影同步失败时要阻止相关群发送或标记为待重建，不能只记录日志后继续允许发送。

## 群聊消息链路

### 1. 客户端发送

沿用现有群聊发送接口、正文限制和客户端 UUID。HTTP 请求包含：

- `group_id`；
- `client_message_id`；
- 消息正文。

前端继续使用发送中、成功、失败重试的简单体验，不新增 accepted/persisted 用户界面状态。

### 2. 群聊 Redis Lua 接纳

群聊脚本独立于私聊脚本，按以下顺序执行：

1. 判断群未解散；
2. 判断发送者当前属于群且具备发送权限；
3. 查找群聊幂等记录；
4. 相同正文返回原消息结果；
5. 相同客户端消息号但正文不同返回冲突；
6. 使用统一 Redis 计数器分配 `server_message_id`；
7. 写入群消息实体和发送者身份快照；
8. 写入群统一信箱；
9. 写入独立群聊 Stream；
10. 更新群接纳水位；
11. 返回 `accepted` 或 `duplicate`。

非成员、被踢成员、已退群成员、已解散群和非法消息必须在分配消息号前拒绝。

Redis 已启用但不可用时，群聊发送返回 `503 message_service_unavailable`，不静默回落到 MySQL，避免同一实例在两套消息号和幂等规则之间混用。完全未配置 Redis/RabbitMQ 时，才继续使用旧 MySQL 直写路径。

### 3. HTTP 和 WebSocket

Lua 成功后 HTTP 立即返回完整群消息：

```text
201 accepted   首次接纳
200 duplicate  已知重复请求
```

在线群成员通过现有连接收到群消息事件。事件应包含完整消息、群 ID、服务端消息号和客户端消息号，客户端以消息号和客户端消息号去重。发送者是否收到自己的 WebSocket 事件继续遵循现有群聊行为，不在 v1.3 引入新的展示规则。

### 4. 群 Stream 到 RabbitMQ

群 Stream 使用独立 consumer group，群事件投递到独立 RabbitMQ exchange、queue 和 routing key：

```text
群 Stream → 群 RabbitMQ exchange → 群持久化 queue → MySQL
```

群事件 envelope 至少包含：

- 消息类型；
- `server_message_id`；
- `group_id`；
- `sender_id`；
- `client_message_id`；
- 正文；
- 创建时间。

群 relay 和群 consumer 可以复用 v1.2 的连接、确认和生命周期骨架，但业务解码、队列名称、Stream key 和 MySQL 持久化方法独立实现。Malformed、身份冲突和不可修复消息必须有可诊断日志；完整死信和重放留到 v1.7。

### 5. MySQL 异步落库

新增群聊幂等持久化方法，显式写入 `server_message_id`，不使用 `LastInsertId` 生成对外消息号：

- `server_message_id` 重复且内容相同，返回幂等成功；
- `(group_id, sender_id, client_message_id)` 重复且内容相同，返回幂等成功；
- 同一幂等键对应不同正文，返回 `ErrMessageConflict`；
- MySQL 事务提交成功后 RabbitMQ consumer ack；
- 临时数据库错误不 ack，允许基础重试；
- 不重新依赖好友关系判断，群成员权限在接纳阶段完成。

## 最低热读和现有群行为兼容

v1.3 不完成 v1.4 的完整 Redis 读取，但需要保证异步窗口内的基本可见性：

- 发送 HTTP 响应包含完整消息；
- WebSocket 事件包含完整消息；
- 群历史最新页支持 Redis 热消息与 MySQL 结果合并；
- `before_id` 和 `after_id` 支持热消息补收；
- 结果按群消息号排序并去重；
- 被踢、退群或非成员不能通过热读绕过 MySQL 群成员权限检查。

实现群热读时要同时修正 v1.2 私聊热读的初始页方向：无 `before_id`、无 `after_id` 时应返回最新消息页，而不是最早消息页。该修复需要补充 `limit` 截断测试，避免群读实现复制已有错误。

由于消息可能先进入 Redis 再进入 MySQL，v1.3 需要使用群接纳水位修正现有群未读和入群起点的短暂窗口，避免消息落库后未读回弹或新成员把入群前的热消息算成新消息。完整群未读 Redis 化和群已读模型仍留给 v1.6。

## 验收方向

1. 群成员可以发送新消息，非成员、被踢、已退群和已解散群在分配消息号前被拒绝。
2. 相同客户端消息号重试返回原消息，不新增 Redis 实体、群信箱索引、Stream 事件或 MySQL 行。
3. 同一群聊幂等键使用不同正文时返回 `409 client_message_id_conflict`。
4. 群消息使用与私聊一致的客户端消息号和服务端消息号生成规则，分别写入 `group_messages`。
5. 在线群成员可以收到完整 WebSocket 消息，重复 HTTP/WS 事件不会重复显示。
6. Redis 已接纳但尚未落库时，发送响应、WebSocket 或群热读仍能获得消息。
7. RabbitMQ 重复投递不会产生重复群消息行，MySQL 提交成功后才 ack。
8. 群历史、分页、入群历史、踢出、退群、解散和现有群未读行为继续兼容。
9. 8199 验证实例与正式 8198 使用隔离的数据库、Redis key、Stream 和 RabbitMQ 拓扑。
10. v1.3 不以群聊已读、高可用故障转移、压力指标或容量指标作为验收条件。
