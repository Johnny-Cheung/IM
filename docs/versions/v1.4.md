# v1.4 Redis 消息读取链路与读取优化

状态：讨论中（2026-10-26），尚未开始编码。

## 目标

在 v1.2 私聊、v1.3 群聊的消息链路之上，把读取路径从「MySQL 为主、Redis 补充热数据」改为「Redis 命中即返回、MySQL 兜底冷数据」，并统一私聊和群聊的游标、翻页、断线补收和会话列表读取规则。

本版不实现私聊/群聊已读位置迁移（v1.5/v1.6），不做 pending 接管、对账、死信和故障转移（v1.7），不做压力测试和容量调优（v1.8）。

## 已确认决策

### 读取口径

- 读取采用 **Redis-first + MySQL 兜底**，不是 Redis-only。Redis 承担热窗口读取，MySQL 始终是全量、权威的历史存储。
- 判断是否可以直接返回 Redis 结果，需要显式的窗口覆盖判定；覆盖不足时必须回落 MySQL，不允许猜测。

### Redis 数据生命周期

- **消息实体不设 TTL**。原先的 24 小时过期会让索引与内容脱节，开发测试期也不便于反复验证。
- **索引不做数量裁剪**。原 `inbox`/`outbox` 每用户 5000 条的 `ZREMRANGEBYRANK` 已移除。
- 两条合计保证：**索引只增不减，实体只增不减，索引中的每个消息号都一定能在 Redis 里取到内容**。
- 去重键继续保留 7 天 TTL，与已读无关，过期不影响读取正确性。
- 时间型 TTL 和窗口裁剪统一推迟到可靠性与容量治理阶段（v1.7/v1.8）设计。

### 已知代价

- 当前 Redis 内存无界增长。开发测试量级不构成问题，但正式实例长期运行会持续占用。
- Redis 配置为 `maxmemory 64mb` + `maxmemory-policy noeviction`，写满后写入失败，表现为发送接口 503。
- 因此正式切换 `8198` 前，至少要落地以下之一：重新引入可验证的窗口边界，或在 `/ops/infra` 暴露 Redis 内存用量并纳入发布检查。该门槛写入本版验收条件。

## 实现变更记录

2026-10-26，按上述决策调整现有链路：

- `backend/internal/messaging/lua/accept.lua`：移除消息实体 `EXPIRE` 和 `inbox`/`outbox` 的 `ZREMRANGEBYRANK`。
- `backend/internal/messaging/lua/group_accept.lua`：移除消息实体 `EXPIRE` 和群信箱的 `ZREMRANGEBYRANK`。
- `RedisAcceptorOptions` 移除 `EntityTTL`、`InboxKeep`、`OutboxKeep`，保留 `DedupTTL` 和 `StreamMaxLen`。
- 新增单元测试：连续接纳多条消息后索引条数与实体数一致，且实体无过期时间。

## 现状问题

v1.3 结束时读取路径的实际形态：

1. **私聊热读未按会话隔离**。`RedisMessageReader` 从整用户的 `inbox`/`outbox` 各取 `limit+1` 条最新消息号，再用 `sameConversation` 过滤。多会话用户下，当前会话的热消息可能被其他会话挤出窗口。
2. **没有窗口覆盖判定**。读取层无法判断某次请求的区间是否被 Redis 完整覆盖，因此不能安全跳过 MySQL。
3. **MySQL 查询没有减少**。`listMessages` 无条件先查 MySQL 整页，Redis 只做叠加，读取优化尚未产生效果。
4. **会话列表依赖 4 次 MySQL 查询**，未读数使用 `COUNT(*)`，且已接纳未落库的消息不计入。
5. **群聊同样是 MySQL-first**，只是群信箱本身按群隔离，比私聊的整用户索引更准确。

## 待讨论

- 私聊是否改为「方向索引」（`dm:conv:{reader}:{peer}`），以获得会话隔离和可直接计算的未读数。
- 窗口覆盖标记（`floor`）的写入时机和缺失时的保守策略。
- 会话列表是否纳入本版，以及未读数在 Redis 与 MySQL 之间的合并规则。
- 群聊是否同版完成，还是先私聊后群聊分两步。
- Redis 冷启动和被清空后的懒加载重建方式。
- 与 v1.5 私聊已读的边界：本版只负责读取，不改变已读语义。
