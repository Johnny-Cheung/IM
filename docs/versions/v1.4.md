# v1.4 服务端消息读取链路

状态：讨论中（2026-10-26），设计已基本确认，尚未开始编码。

## 目标

把读取路径从「MySQL 为主、Redis 只补充热数据」改为「Redis 命中即返回、MySQL 兜底冷数据」，并统一私聊与群聊的游标、分页、断线补收和回落规则。

本版只做服务端。Web 端本地缓存与增量同步属于 v1.5；私聊已读属于 v1.6；群聊已读属于 v1.7；可靠性与一致性属于 v1.8；容量验证与调优属于 v1.9。

## 现状问题

v1.3 结束时的读取路径：

1. **私聊热读未按会话隔离**。`RedisMessageReader` 从整用户的 `inbox`/`outbox` 各取 `limit+1` 条最新消息号，再用 `sameConversation` 过滤。多会话用户下，当前会话的热消息可能被其他会话挤出窗口。
2. **没有读取覆盖判定**。读取层无法判断某次请求的区间是否被 Redis 完整覆盖，因此不能安全跳过 MySQL。
3. **MySQL 查询没有减少**。`listMessages` 无条件先查 MySQL 整页，Redis 只做叠加，读取优化尚未产生效果。
4. **会话列表依赖 4 次 MySQL 查询**，未读数使用 `COUNT(*)`，且已接纳未落库的消息不计入。
5. **群聊同样是 MySQL-first**，只是群信箱本身按群隔离，比私聊的整用户索引更准确。

## 已确认决策

### 1. Redis 数据不设时间边界

- 消息实体不设 TTL；索引不做数量裁剪。
- 索引只增不减、实体只增不减，因此索引中的每个消息号都一定能取到内容。
- 去重键继续保留 7 天 TTL，与读取无关。
- 时间型 TTL 和窗口裁剪推迟到 v1.9 的容量治理设计。

### 2. 三类索引

| 结构 | 键 | 数量 | 内容 |
| --- | --- | --- | --- |
| 用户级增量日志 | `dm:feed:{userID}` | 每用户 1 个 | 该用户参与的全部私聊消息号 |
| 会话索引 | `dm:conv:{ownerID}:{peerID}` | 每对好友 2 个 | 一个方向的消息号 |
| 群索引 | `group:{groupID}:inbox` | 每群 1 个 | 群消息号，保持现状 |

三个都是 ZSET，`member` 和 `score` 都是 `server_message_id`，只存消息号，不存正文。

`dm:conv:{ownerID}:{peerID}` 的语义固定为 **peer 发给 owner 的消息**。一对好友有两个键，分别对应两个方向；双方读取时合并这两个键。

一条私聊消息写入三次，全部在同一个 Lua 脚本内原子完成：

```text
sender 的 feed
recipient 的 feed
dm:conv:{recipient}:{sender}
```

### 3. 覆盖判定使用全局 epoch

```text
im:v12:index:epoch   STRING   此消息号以下不保证已建索引
```

- 上线时写入当时的 `MAX(server_message_id)`；
- 使用 `SET NX` 写入，重启不会推高 epoch；
- Redis 被清空后，启动时重新播种；
- 判定规则：**只有大于 epoch 的区间，索引才是完整的**；
- 游标落在 epoch 以下时，一律回落 MySQL，不能返回空。

私聊和群聊共用同一个 epoch，因为两者共用同一个消息号段。

### 4. 读取规则

| 请求 | 数据源 | 直接返回 Redis 的条件 |
| --- | --- | --- |
| 全局增量（重连/打开页面） | `dm:feed:{me}` | cursor ≥ epoch，一条范围查询 |
| 会话最新页 | 两个 `dm:conv` | 合并后取到 `limit+1` 条 |
| 会话 `before_id` | 两个 `dm:conv` | 合并后取到 `limit+1` 条 |
| 会话 `after_id` | 两个 `dm:conv` | `after_id ≥ epoch` 且尾部一致 |
| 群消息 | `group:{id}:inbox` | 与私聊相同的 epoch 规则 |

`before_id` 取不满 `limit+1` 时无法区分「确实到底」和「再往下还有」，因此必须回落 MySQL。这是保守策略：边界附近多查一次数据库，但不会漏消息。

### 5. 回落时仍然合并热数据

已接纳未落库的消息不在 MySQL 里，所以回落路径是：

```text
MySQL 整页  +  Redis 中 id > epoch 的该会话消息
            → 按消息号排序去重 → 截断 limit
```

与现有 `mergeMessagePages` 的逻辑一致，区别是 Redis 侧按会话精确读取。

### 6. 旧索引退役

- `inbox`/`outbox` 停止写入，读取路径不再使用；
- 因为 Redis 不是权威存储，删除是安全的；
- 保留一个版本用于回滚兜底，确认稳定后按前缀清理；
- 回滚到旧版本时，切换后产生的消息仍在 MySQL 中，历史不会丢。

## 实施小步

### Step 1：键与 epoch

- 新增 `directFeedKey`、`directConversationKey`；
- 新增 epoch 键和 `SET NX` 播种逻辑；
- 启动时随消息号水位一起初始化。

### Step 2：写入改为三类索引

- `accept.lua` 从两次 `ZADD` 改为三次；
- `accept.go` 构造新的键列表；
- 保持好友校验、去重、冲突、消息号分配、实体和 Stream 不变。

### Step 3：读取层重写

- `RedisMessageReader` 改为按会话读取两个方向键；
- 增加 epoch 覆盖判定；
- 保持方法签名不变，HTTP 层无需感知。

### Step 4：合并与回落

- 保留 MySQL 回落路径；
- 回落时只合并该会话的热数据；
- 保持分页方向、`has_more` 和排序语义不变。

### Step 5：群聊复用

- 群读取复用同一套 epoch 判定；
- 群范围查询本来就按群隔离，只调整「是否跳过 MySQL」的判断。

### Step 6：会话列表（可选）

- 本版可以先不改会话列表，继续使用 MySQL；
- 若纳入，只让最后一条消息支持 Redis 热数据；
- 未读数仍走 MySQL，Redis 化留到 v1.6。

### Step 7：验证与切换

- 单元测试覆盖会话隔离、三种游标、epoch 边界和回落合并；
- 隔离环境验证队列清空后切换；
- 正式切换前确认 RabbitMQ 私聊与群聊队列 `ready/unack = 0`。

## 验收方向

1. 读某个会话时，Redis 只返回该会话的消息，不再依赖事后过滤。
2. 会话最新页、`before_id`、`after_id` 在 Redis 覆盖范围内不访问 MySQL。
3. 游标低于 epoch 时正确回落 MySQL，且不丢消息、不回退。
4. 已接纳未落库的消息在回落路径中仍可见。
5. 群聊读取行为与 v1.3 兼容。
6. `feed` 能一次返回重连期间的全部新私聊消息。
7. 现有私聊/群聊历史、分页、未读和已读行为不变。

## 不在本版范围

- 私聊已读位置、未读 Redis 化（v1.6）；
- 群聊已读（v1.7）；
- Web 端本地缓存与首屏优化（v1.5）；
- 群消息的 per-user fanout；
- pending 接管、死信、对账、多实例（v1.8）；
- 压力测试和容量调优（v1.9）。

## 已知风险

- Redis 内存无界增长。开发测试阶段可接受，正式切换前必须落地内存观测或窗口边界方案，否则写满 64 MB 后发送接口会返回 503。
