# v1.5 Web 端本地缓存与增量同步

状态：方案已对齐（2026-10-26），尚未开始实现。

## 目标

让浏览器在打开页面时先用本机缓存渲染，再后台与服务端对齐：

- 刷新、重开页面时，会话列表和最近消息立刻出现，不白屏、不等网络；
- 网络暂时不可用时仍可只读查看已缓存的消息；
- 冷启动的 HTTP 请求从现在的 3 次（鉴权、会话、好友）加增量请求，收敛为 **1 次**。

v1.5 只做 Web 端缓存和增量同步。服务端读取链路已在 v1.4 完成；私聊已读属于 v1.6，群聊已读属于 v1.7，可靠性与一致性属于 v1.8，容量验证属于 v1.9。

## 已确认决策

1. **离线只读。** 断网时可以使用缓存查看历史；发送、加好友、建群等写操作仍然要求在线，不做离线发送队列。
2. **缓存按账号隔离。** 所有缓存以用户名为键；退出登录时清除该账号在本机的缓存。
3. **保留量。** 每个会话最近 200 条，全账号最多 10000 条；超出后按最久未使用淘汰整个会话的缓存。上翻到缓存边界时照常向服务端请求，用户无感。
4. **冷启动合并为一个请求。** 新增 `/api/bootstrap`，一次返回当前用户、会话列表、好友列表、私聊增量和有变化的群增量。
5. **群聊不遍历。** 客户端提交本地每个群的游标，服务端用会话列表做内存比较，只读取最后一条消息比游标新的群；没有变化的群不产生 Redis 或 MySQL 读取。
6. **只有同步响应推进游标。** WebSocket 推送和发送响应都不推进游标，避免跳过中间消息。
7. **服务端是权威。** 每次上线都以服务端返回的会话列表、好友列表和增量覆盖本地；增量不完整时标记本地私聊缓存不可信，等打开会话时再拉最新页。

## 启动流程

```text
读取本地账号提示和游标（IndexedDB）
        ↓
POST /api/bootstrap（1 次）
        ↓
401 → 游客；网络失败且有缓存 → 离线只读；200 → 写回缓存并渲染
        ↓
后台应用私聊增量、群增量
        ↓
连接 WebSocket，之后实时推送；不推进同步游标
```

### 离线模式

- 只有在“本地有账号提示和缓存 + 请求网络失败”时进入离线模式；
- 离线模式下显示缓存内容，隐藏或禁用发送入口，并提示“当前离线，只能查看已缓存消息”；
- 服务端返回 401 时不进入离线模式，按现有逻辑回到登录页；
- 这是本机缓存的固有限制：浏览器无法在断网时验证会话是否仍然有效。缓存只在已登录过的同一台设备上可见。

## `/api/bootstrap`

`POST /api/bootstrap`，需要登录，请求体：

```json
{
  "after_id": 1234,
  "groups": [{ "group_id": 12, "after_id": 880 }],
  "limit": 200
}
```

- `after_id`：本地私聊同步游标；首次登录为 0；
- `groups`：本地已缓存的群游标，最多 200 项；服务端只处理同时存在于当前用户会话列表中的群；
- `limit`：私聊增量条数，默认 200，服务端上限 200。

响应：

```json
{
  "user": { "username": "...", "nickname": "..." },
  "conversations": [],
  "friends": [],
  "direct": {
    "messages": [],
    "has_more": false,
    "complete": true,
    "cursor": 1400
  },
  "groups": [
    { "group_id": 12, "messages": [], "has_more": false, "complete": true, "cursor": 905 }
  ],
  "partial": []
}
```

规则：

- `cursor` 由服务端给出，客户端只接受比本地更大的值；
- 群游标为 0 或缺失表示本地没有该群缓存，服务端跳过，打开会话时拉最新页；
- `complete=false` 表示私聊增量没有覆盖本地游标到当前区间，客户端把本地私聊缓存标记为不可信；群增量的 `complete` 逐群返回，为 false 时该群在打开时重新拉最新页；
- 群增量每群最多 50 条，全部群合计最多 200 条；超出的用 `has_more` 标记，客户端空闲时继续拉或等打开会话；
- 群增量整体预算 300ms，超时先返回其他部分，并在 `partial` 中标记 `groups`；
- 会话、好友、私聊、群任一部分失败时仍返回其他部分，`partial` 列出缺失的段落；
- 响应总条数上限 400 条，超过时优先保证私聊，群增量截断并标记。

现有 `/api/conversations`、`/api/friends`、`/api/messages/sync` 保持可用，`/api/messages/sync` 增加服务端计算的 `cursor` 字段；其他页面和测试不需要改动。

## 本地数据模型

使用 IndexedDB，数据库 `im-cache`，版本 1。

| 对象仓库 | 键 | 内容 |
| --- | --- | --- |
| `meta` | `active-user`、`{user}:sync` | 最近账号提示；游标、群游标、同步时间和缓存可信标记 |
| `conversations` | `[user, conversationKey]` | 会话对象、缓存时间 |
| `messages` | `[user, conversationKey, id]` | 原始 `ChatMessage` / `GroupMessage` |
| `friends` | `[user]` | 好友列表 |

- `conversationKey` 沿用前端现有的 `direct:{username}` 和 `group:{id}`；
- 消息按服务端消息号排序，读取时转成现有的展示结构；
- 只缓存服务端确认过的消息，不缓存“发送中”或“失败”的临时消息；
- 数据库版本变化时直接清库重建，缓存视为可丢弃数据；
- 不缓存密码、会话 Cookie、WebSocket 凭据等敏感信息。

### 淘汰

- 每个会话保留最近 200 条；
- 全账号最多 10000 条、最多 100 个带消息的会话；
- 超出后按最后活跃时间淘汰整个会话的消息缓存，会话列表本身保留；
- 淘汰只影响本地，不影响服务端历史。

## 前端接入点

### 认证

- `AuthProvider` 改用 `/api/bootstrap` 作为会话检查，不再单独请求 `/api/me`；
- 登录成功后立即执行一次 bootstrap，填充缓存和界面；
- 新增离线状态；离线时保留缓存渲染能力，写操作统一提示需要联网。

### 会话列表

- 打开页面时先读本地会话和好友并渲染；
- bootstrap 返回后以服务端列表为准，合并规则：
  - 同一会话取最后一条消息号更大的；
  - 未读数以服务端为准；
  - 服务端已不存在的会话，删除本地消息缓存（仅在会话列表请求成功时执行）；
- bootstrap 期间到达的 WebSocket 事件先缓冲，bootstrap 应用后再处理，避免覆盖新消息和未读。

### 打开会话

1. 从本地读该会话最近 200 条，立即渲染；
2. 如果会话列表显示的最后一条消息号大于本地最新消息号，拉取增量并合并；
3. 拉取期间继续展示缓存，不显示整页加载状态；
4. 本地没有该会话缓存时，按现有逻辑拉最新页。

### 上翻历史

- 本地还有更早的消息时直接展示，不请求；
- 到达缓存边界后，使用现有 `before_id` 接口继续分页；
- 缓存记录该会话“是否已到达最早一条”，避免到底后重复请求。

### 实时消息与发送

- WebSocket 消息写入缓存，并按现有逻辑更新会话列表；
- 发送成功（HTTP 确认）后写入缓存；发送中、失败状态只存在于内存；
- 已读事件更新会话未读数，同步写回缓存。

### 退出登录

- 清除当前账号的 `conversations`、`messages`、`friends` 和同步状态；
- 清除账号提示；
- 清除失败不阻塞退出，但下次登录会覆盖旧数据。

## 一致性与竞态

1. **去重键**：`server_message_id` 优先，`client_message_id` 兜底。
2. **游标单调**：本地游标只增不减；服务端返回更小的游标时忽略。
3. **游标来源**：只有 bootstrap 和同步响应能推进游标；WebSocket、发送确认、已读事件都不推进。
4. **增量不完整**：`complete=false` 时把私聊缓存标记为不可信；打开会话时重新拉最新页，成功后恢复可信。
5. **多标签页**：两个标签页共享缓存，重复写入按消息号幂等；不做跨标签广播，后写的覆盖先写的，内容一致。
6. **账号切换**：账号提示与 bootstrap 返回的用户不一致时，丢弃本次基于提示读取的游标和缓存，按新用户重新渲染；bootstrap 返回数据仍然有效。

## 降级

- 浏览器不支持 IndexedDB、隐私模式不可用或写入配额不足：本次会话停用缓存，退回现有网络加载行为，不阻塞使用；
- 每次 bootstrap 写入后主动执行淘汰；写入过程中遇到配额错误时只停用缓存，不在错误路径上重试；
- 缓存损坏或版本不匹配：清库重建，不向用户报错；
- bootstrap 失败但本地有缓存：进入离线只读；
- bootstrap 失败且无缓存：显示现有错误提示和重试入口。

## 验收方向

1. 已登录用户刷新页面时，会话列表和当前会话消息在 bootstrap 返回前已经可见。
2. 冷启动只有 1 次 `/api/bootstrap` 请求，外加 WebSocket 连接。
3. 断网后已打开的页面仍能查看已缓存会话和消息，发送入口提示需要联网；彻底断网后重新打开页面能否渲染取决于浏览器是否还能加载应用外壳。
4. 重新联网后，私聊和群聊增量补齐，无重复、无缺失、顺序正确。
5. 打开没有新消息的会话不产生额外请求；打开有新消息的会话只拉增量。
6. 上翻历史在缓存范围内不发请求，超出后正常分页。
7. 退出登录后再登录其他账号，看不到前一个账号的任何缓存内容。
8. 浏览器禁用 IndexedDB 或写入失败时，功能退回现有行为，不出现空白页或报错。
9. 现有私聊、群聊、未读、已读、分页和断线补收行为不变。
10. 8199 验证实例与正式 8198 使用隔离的数据库、Redis 和 RabbitMQ，测试数据按 manifest 清理。

## 不在本版范围

- 离线发送队列、联网后自动补发；
- Service Worker、后台同步、推送通知；
- 多设备之间同步已读位置；
- 本地数据加密；
- 群成员、群详情、好友申请的缓存；
- 私聊已读（v1.6）、群聊已读（v1.7）；
- 消息实体 TTL、容量治理和性能压测（v1.9）。

## 风险

1. **离线模式的会话有效性无法验证。** 断网时只能信任本机账号提示；如果会话已在服务端失效，缓存仍会显示。缓解：只在同一设备显示、不提供写操作、退出登录立即清缓存。
2. **bootstrap 成为单点。** 一个接口承担四块数据，任一慢都会影响首屏。缓解：分段限额、群增量 300ms 预算、`partial` 部分返回。
3. **缓存与服务的短暂不一致。** WebSocket、bootstrap 和本地发送可能交错。缓解：按消息号幂等合并、游标只由同步响应推进、bootstrap 期间缓冲实时事件。
4. **IndexedDB 兼容性和配额。** 隐私模式、旧浏览器和配额不足都可能失败。缓解：统一降级到网络加载。
5. **前端测试基础薄弱。** 现有前端没有测试框架。缓解：只对纯逻辑和缓存层引入 Vitest，界面行为继续由浏览器 smoke 覆盖。
6. **离线冷启动依赖应用外壳。** v1.5 不引入 Service Worker；如果浏览器在完全离线时无法加载页面本身，本地缓存也不会被读取。已打开的页面断网不受影响。
