# v1.6 私聊已读

状态：方案已确认，待实现（2026-10-27）。

## 目标

把私聊已读的读状态（已读位置、未读数、对方回执）从 MySQL 热路径迁到 Redis，解决 v1.2 起就存在、v1.4 仍未收敛的异步落库窗口问题：

- 消息已进入 Redis、已通过 WebSocket 推送、但尚未落 MySQL 时，接收方标记已读不会停在旧消息号；
- 未读统计包含已接纳未落库的消息，刷新页面不会出现“消息已显示、未读为 0”；
- 发送方的“已读”回执不因落库延迟而后退；
- 标记已读、未读计算和回执查询不查 MySQL；
- 用户可见行为保持 v0.5/v0.7 基线不变。

v1.6 只做私聊。群聊已读属于 v1.7，可靠性和多实例属于 v1.8，容量治理属于 v1.9。

## 已确认决策

1. **会话级水位，不是逐条回执。** 每个“用户 + 对方”只保存最后已读消息号；发送方仍只在自己的最后一条消息下显示“已读/未读”。
2. **只存位置，不存未读数。** 未读数由 `ZCOUNT` 现算，不引入计数器，避免漂移和重建。
3. **已读位置放 Redis。** `dm:read:{userID}` 为 HASH，字段是对方向 user ID，值是最后已读消息号；MySQL `conversation_reads` 只做异步持久化和重建来源。
4. **未读和回执都从现有消息索引派生。** 未读使用 `dm:conv:{我}:{对方}` 的 `ZCOUNT`；对方的已读位置直接读对方的 `dm:read`。
5. **已读上界来自 Redis 已接纳消息。** 取 `dm:conv` 中 `<= through_id` 的最大消息号，不再使用 MySQL 的 `MAX(server_message_id)`。
6. **只有真正推进才发事件。** 位置只增不减；并发和重复标记不会回退，也不会乱序发送 `messages.read`。
7. **新增批量已读接口。** 切换会话时把旧会话和新会话的位置放在同一次请求里；保留现有单会话接口供兼容。
8. **历史数据一次性回填。** 把 MySQL 私聊消息号写入 `dm:conv`，把 `conversation_reads` 写入 `dm:read`；不回填则老会话的未读仍需查 MySQL。
9. **鉴权仍走现有会话表。** 本版只保证读状态的计算和写入不查 MySQL，不要求整个 HTTP 请求零 MySQL。
10. **生产环境 Redis 故障时已读接口返回 503。** 不回落 MySQL，避免用不完整数据冒充正确结果。
11. **群聊未读和已读完全不变。** 批量接口只处理私聊。
12. **多设备、多标签页语义不变。** 仍为单会话、单连接；刷新或换设备后从服务端恢复位置。

## 数据模型

### Redis

| 键 | 类型 | 内容 |
| --- | --- | --- |
| `dm:read:{userID}` | HASH | 字段为对方 user ID，值为最后已读消息号 |
| `dm:conv:{ownerID}:{peerID}` | ZSET | 复用 v1.4：peer 发给 owner 的消息号 |
| `dm:read:stream` | Stream | 已读位置变更事件，供异步持久化 |
| `dm:read:ready` | STRING | 历史回填完成标记 |

- `dm:read` 不设 TTL；与 v1.4 的消息索引保持一致，容量治理留到 v1.9。
- 不新增反向索引。对方的已读位置通过读取对方的 `dm:read` 获取，会话列表用 pipeline 一次取回。
- `dm:read:stream` 使用 `MAXLEN ~ 10000` 控制长度。

流事件字段：

```text
user_id、peer_id、last_read_message_id、updated_at_ms
```

### MySQL

- `conversation_reads(user_id, peer_user_id, last_read_message_id, updated_at)` 保持不变，不需要迁移。
- 写入改为异步消费：`INSERT ... ON DUPLICATE KEY UPDATE last_read_message_id = GREATEST(...)`，重复和乱序消费都幂等。
- MySQL 仍是持久化和重建来源，但不在已读请求链路上。

## 接口

### 批量已读

```text
POST /api/read
```

请求：

```json
{
  "reads": [
    { "username": "bob", "through_id": 105 },
    { "username": "carol", "through_id": 88 }
  ]
}
```

- 需要登录；一次最多 50 项；
- `through_id` 缺省或为 0 时，表示推进到对方已接纳的最新消息；
- 每一项独立处理，互不影响。

响应：

```json
{
  "reads": [
    { "username": "bob", "last_read_message_id": 105, "advanced": true },
    { "username": "carol", "last_read_message_id": 88, "advanced": false }
  ]
}
```

- 单项失败时该项返回 `error`（例如 `user_not_found`、`cannot_message_self`），其他项照常生效；
- 请求体格式错误或超过 50 项返回 400；未登录返回 401；
- 只有 Redis 不可用时返回 503，前端保留该项并重试。

### 单会话已读（兼容）

```text
POST /api/conversations/:username/read?through_id=N
```

- 路径、参数和响应保持不变；
- 内部与批量接口共用同一套推进逻辑；
- 旧客户端不受影响。

### WebSocket 事件

`messages.read` 保持不变：

```json
{
  "type": "messages.read",
  "reader": "alice",
  "peer": "bob",
  "last_read_message_id": 105
}
```

- 只在位置真正推进时发送；
- 发给已读方和对方；
- 客户端对同一会话取最大值，乱序或重复事件不会回退。

## 标记已读流程

1. 校验登录用户和目标用户，拒绝给自己标记；
2. 计算候选位置：

```text
through_id > 0:
  ZREVRANGEBYSCORE dm:conv:{我}:{对方} through_id -inf LIMIT 0 1
through_id = 0:
  ZREVRANGE dm:conv:{我}:{对方} 0 0
```

3. 没有候选位置时，不推进，返回当前已有位置（没有则为 0）；
4. 一段 Lua 原子完成：
   - 读取 `HGET dm:read:{我} {对方}`；
   - 候选位置更大才 `HSET`；
   - 同时 `XADD dm:read:stream`；
   - 返回最终位置和是否推进；
5. 只有推进时才发布 `messages.read`；
6. 响应返回最终位置。

并发标记同一会话时，Redis 串行执行 Lua：只有第一次推进成功，后续较小的位置不会回退，也不会重复发送事件。

## 未读与回执

会话列表和 bootstrap 的私聊项按下面计算：

```text
我的已读位置   pos = HGET dm:read:{我} {对方}，没有则为 0
未读数         unread = ZCOUNT dm:conv:{我}:{对方} (pos +inf
对方读我到哪   HGET dm:read:{对方} {我}，没有则为 0
```

- 我的全部位置用一次 `HGETALL dm:read:{我}` 取回；
- 每个会话的 `ZCOUNT` 和对方的 `HGET` 放进同一个 pipeline；
- `dm:conv` 只包含对方发给我的消息，自己发的消息不会计入未读；
- 未读包含已接纳但尚未落 MySQL 的消息；
- 没有对方发来的消息时未读为 0；
- 群聊会话的未读仍按 v1.3 逻辑，不进入本模型。

### 历史覆盖

`dm:conv` 在 v1.4 之前只覆盖部分消息。v1.6 上线前必须完成回填，否则老会话的未读仍不完整。回填后的老消息在历史分页中仍被 epoch 过滤，不改变现有历史读取行为，只服务于未读计算。

### 无 Redis 的本地开发

未配置消息基础设施时，`directReader` 为空：标记已读、未读和对方已读继续使用 MySQL 路径，行为与 v1.5 一致。生产环境必须启用 Redis 读模型。

## 异步持久化

- 标记已读成功写入 Redis 后，事件进入 `dm:read:stream`；
- 后台 worker 使用 consumer group `dm-read-persist` 消费；
- 每批事件按 `GREATEST` 写入 `conversation_reads`，成功后才 ack；
- MySQL 临时错误不 ack，退避重试；格式错误记录日志后 ack，避免阻塞；
- 消费者名包含主机和进程标识，为 v1.8 多实例预留；
- Stream 被裁剪导致事件丢失时，MySQL 可能落后，但 Redis 仍是权威；重建和对账属于 v1.8。

## 历史回填

一次性命令，幂等，可在服务运行时执行：

1. 记录起始水位 `cutoff = MAX(server_message_id)`；
2. 分批读取 `messages` 的 `server_message_id`、`sender_id`、`recipient_id`，向接收方的 `dm:conv:{recipient}:{sender}` 执行 `ZADD`；
3. 分批读取 `conversation_reads`，写入 `dm:read:{user_id}` 的 `peer_user_id` 字段；
4. 校验：按会话比较 MySQL 消息数与 `ZCARD`，按用户比较已读位置；
5. 校验通过后写入 `dm:read:ready=1`；
6. 记录 Redis `used_memory` 增量。

回填期间新消息由 `accept.lua` 正常写入，`ZADD` 幂等；回填只处理起始水位以内的历史，不覆盖新消息。

生产环境启用消息链路时：

- 启动前必须存在 `dm:read:ready`，否则拒绝启动；
- 运行期间每次读状态请求检查该标记，Redis 丢数据后返回 503，直到重新回填完成。

## 前端

### 待上报队列

前端维护 `pendingReads`，键为会话，值为待上报的最大消息号：

- 同一会话多次变化只保留最大值；
- 队列持久化到 IndexedDB `meta`，键为 `{user}:pending-read`，离线或页面崩溃后可恢复；
- 只保存私聊；群聊继续使用现有逻辑。

### 上报时机

- **切换会话**：把旧会话和新会话一起放入队列并立即上报，一次请求更新两个位置；
- **当前会话持续来消息**：合并到同一项，按 1 秒节流上报，避免持续消息把定时器饿死；
- **页面隐藏、卸载、刷新前**：尽力补发；
- **恢复联网、重连**：补发队列；
- **定时器到期**：兜底。

### 本地状态

- 打开会话时，本地未读先清零到当前已加载的最大消息号，之后到达的新消息重新计入；
- 批量已读成功后，用响应中的位置更新本地未读和已读位置，不整表刷新会话列表；
- 收到自己的 `messages.read` 回声时只更新本地，不再触发第二次会话列表刷新；
- 对方回执按会话取最大值，用户名字母大小写不敏感；
- 批量请求中永久失败（用户不存在、不能给自己标记）的项从队列移除；临时失败保留重试；
- 退出登录时清除待上报队列和该账号缓存。

### 缓存

- `unread_count` 和 `peer_last_read_message_id` 继续写入 v1.5 的 IndexedDB 会话缓存；
- 离线冷启动显示缓存值，联网后由服务端覆盖；
- 不新增已读位置缓存表，服务端仍是权威。

## 一致性与竞态

1. **单调**：位置只增不减，所有写入都取较大值。
2. **并发**：Redis Lua 串行执行；只有实际推进的请求发送事件。
3. **乱序**：批量内各会话独立；多个批量请求乱序到达不会回退。
4. **上界**：候选位置来自 Redis 已接纳消息，`through_id` 大于最新消息时自动截断。
5. **无消息**：没有对方发来的消息时不推进、不建字段。
6. **未落库**：已读位置可以大于 MySQL 已落库的最大消息号，这是预期行为；落库后未读不回升。
7. **事件丢失**：`messages.read` 仍是尽力通知；断线或刷新后由会话列表和 bootstrap 的 Redis 值恢复。
8. **异步落库乱序**：MySQL 使用 `GREATEST`，晚到的旧事件不会覆盖新位置。
9. **Stream 裁剪**：极端积压时事件可能丢失，MySQL 短暂落后；Redis 权威，重建留 v1.8。
10. **回填窗口**：回填与正常接纳并行，`ZADD` 幂等，起始水位以内由回填补齐，以上由接纳写入。

## 失败与降级

| 场景 | 行为 |
| --- | --- |
| Redis 不可用 | 标记已读 503；会话列表未读字段标记为部分数据；不回落 MySQL |
| MySQL 不可用 | 已读链路正常；异步持久化积压重试；其他 MySQL 接口按现有逻辑失败 |
| 回填未完成或 Redis 丢数据 | 读状态接口 503，直到重新回填 |
| Stream 积压 | worker 持续消费；超过长度上限可能丢旧事件，MySQL 短暂落后 |
| 浏览器不支持 IndexedDB | 待上报队列只保存在内存，刷新会丢失；恢复联网后由服务端校准 |
| 页面关闭前补发失败 | 未上报位置丢失；下次打开会话时重新标记 |

## 验收方向

1. B 发送消息后，A 立刻标记已读；即使消息尚未落 MySQL，A 的位置也等于已发送消息号，落库后未读保持 0。
2. B 能立即看到 A 的已读位置，不因异步落库延迟而停在旧值。
3. 30 个好友、每人 10 条未读时，会话列表未读逐项正确；上线不查询 MySQL 的已读和未读。
4. 从一个私聊切到另一个私聊，只发一次批量请求，旧会话和新会话的位置都正确更新。
5. 停留在会话内持续收消息，位置最多延迟约 1 秒推进，不按每条消息发请求。
6. 页面切到后台不自动已读；回到前台后位置补齐。
7. 离线阅读后恢复联网，待上报位置自动补发。
8. 刷新页面时未读不闪回、不出现“消息已显示、未读为 0”。
9. 并发或重复标记同一会话，位置不回退，事件不乱序、不重复播报。
10. Redis 不可用时已读接口明确失败；恢复并完成回填后继续工作。
11. MySQL 不可用时已读仍可工作；异步事件在恢复后补齐。
12. 现有私聊历史、分页、未读展示、最后一条消息“已读/未读”和群聊未读行为不变。
13. 退出登录或清除浏览器缓存后重新登录，已读位置从服务端恢复。

## 不在本版范围

- 群聊已读（v1.7）；
- 逐条消息已读回执、已读成员列表；
- 多设备同时在线、多标签实时同步；
- 未读计数器和 Redis 已读反向索引；
- 鉴权会话缓存、整个 bootstrap 零 MySQL；
- Redis 已读键 TTL、容量治理和缓存淘汰；
- 多实例 WebSocket、可靠投递、对账和 pending 接管（v1.8）；
- 压力测试和最终性能目标（v1.9）。

## 风险

1. **Redis 丢数据会丢最近已读。** 异步持久化有窗口；重建后以 MySQL 为准，用户可能看到少量未读回来。v1.8 处理持久化、对账和恢复。
2. **历史回填是前置条件。** 回填不完整会让老会话未读偏小；通过校验和启动标记阻止不完整数据上线。
3. **Stream 积压或裁剪会丢持久化事件。** Redis 仍是权威，但 MySQL 可能落后；v1.8 增加对账。
4. **批量接口的部分失败语义。** 前端必须区分永久失败和临时失败，避免无限重试。
5. **前端待上报队列仍是尽力而为。** 页面崩溃或关闭前补发失败会丢失少量已读，下次打开会话时重新标记。
6. **鉴权仍查 MySQL。** 已读热路径不查 MySQL，但请求本身仍有会话表查询；整个请求零 MySQL 不在本版。
7. **Redis 内存继续增长。** 回填会让 `dm:conv` 明显变大，`dm:read` 随会话数增长；上限仍是 64 MiB + noeviction，容量治理留到 v1.9。
