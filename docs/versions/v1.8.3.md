# v1.8.3 Redis 数据重建与双向一致性检查

状态：方案已确认，待开发（2026-10-29）。属于 [v1.8 可靠性与一致性](v1.8.md)，依赖 [v1.8.1](v1.8.1.md) 的会话消息号 `seq` 和 [v1.8.2](v1.8.2.md) 的可靠投递与对账。

## 目标

Redis 数据整体丢失或部分丢失后，能照着 MySQL 把消息链路需要的 Redis 数据重新生成；运行期间能尽早发现“MySQL 有、Redis 没有”的不一致，少量缺失自动补回，缺失过多时明确告警并要求人工重建。

范围仍只含单体：一个后端进程、一台 Redis、一台 RabbitMQ、一个 MySQL。

## 背景

Redis 是消息链路的读取层和接纳层，MySQL 是最终账本。v1.8.2 的对账只检查一个方向：**Redis 有、MySQL 没有**（已接纳未落库），查到就写 MySQL。反向的不一致没有检查，总丢失只能靠人工处理。

每次后端启动时已经会从 MySQL 重建：

- 好友集合 `friends:*`；
- 群成员、解散标记和群已读水位；
- 每个会话的计数器（校准只抬高）。

缺的是：消息实体、`dm:pair`/`group:{G}:inbox`、`dm:feed`、`dm:conv-last`、私聊已读水位、7 天内的去重记录、全局计数器、`index:epoch` 和 `seq:ready`。

## 已确认决策

1. **重建必须停后端。** 命令拒绝在后端单元运行、`8198`/`8199` 端口监听或同名 `im-server` 进程存在时执行。原因：重建期间历史读取会看到半成品。
2. **重建命令先排空两个持久化队列。** 已在 RabbitMQ、尚未落 MySQL 的消息能救回来：consumer 只依赖消息体，不读 Redis。命令消费到队列为空，毒消息走 v1.8.2 的死信路径并报告；队列在超时内没有排空则中止重建。否则这些消息会在重建后才落库，导致 Redis 缺实体、会话计数器撞号。
3. **只重建 7 天内的去重记录。** 与现有 TTL 一致，更早的记录本来就会过期。
4. **部分丢失由定时检查发现并自动小补；不承诺全部自动修复。** 少量缺失自动补 Redis；超过阈值标记“需要重建”，只告警不硬补。
5. **重跑从头再来。** 失败后清掉本命名空间的已知键重新执行，不做断点续跑。
6. **不切正式 8198。** 开发阶段在 8199 验证；共享 Redis、RabbitMQ、MySQL 容器不重启。
7. **沿用 v1.8 的单体、AOF `everysec`、接纳语义和“不做向后兼容”。**

## Redis 数据与重建来源

键名省略命名空间前缀（正式 `im:v12:`，验证 `im:v13-verify:`）。

| Redis 结构 | 重建来源 | 缺失时的用户可见影响 |
| --- | --- | --- |
| `messages:{id}` | `messages` 行；`body_hash` 重算 | 历史回落 MySQL（正确但慢）；`dm:feed` 判定不完整 |
| `group-messages:{id}` | `group_messages` 行，发送者昵称取用户当前资料 | 同上 |
| `dm:pair:{low}:{high}` | `messages` 按 `seq` 写入 | 历史翻页回落 MySQL |
| `group:{G}:inbox` | `group_messages` 按 `seq` 写入 | 同上 |
| `dm:seq`、`group:{G}:seq` | 每个会话的 `MAX(seq)` | 新消息可能撞号；启动校准会抬高 |
| `dm:feed:{user}` | 每条消息同时写入收发双方 | 私聊增量同步可能漏消息，读取判定不完整 |
| `dm:conv-last:{user}` | 按消息顺序写，后者覆盖前者 | 会话列表预览为空或旧 |
| `dedup`、`group-dedup` | 7 天内的 `client_message_id`，写剩余 TTL | 客户端重发同一条会被当成新消息 |
| `dm:read:{user}` | `conversation_reads.last_read_seq` | 未读数把所有历史都算成未读 |
| `group:{G}:read` | `group_members.last_read_seq` | 群未读和已读人数偏差；启动会重建 |
| `friends:{user}` | `friendships` | 不能发消息；启动会重建 |
| `group:{G}:members`、`dissolved` | `group_members`、`chat_groups.dissolved_at` | 群发送被拒；启动会重建 |
| `messages:next_id` | 两张消息表和服务号表的全局最大值 | 新消息号可能与账本重复 |
| `index:epoch` | 全量重建 feed 后设为 0 | feed 永远被判为不完整，增量同步回落到 MySQL |
| `seq:ready` | 校验通过后最后写入 | 缺失时后端拒绝启动 |
| 读事件 Stream、消息 Stream | 空 Stream；消费组在启动时创建 | 丢失的未持久化已读事件使未读偏多（安全方向） |

## 补不回来的

- **只写入 Redis Stream、尚未发布到 RabbitMQ 的消息。** 随数据一起消失。客户端按 `seq` 对账发现后转成发送失败，可用原客户端 ID 重发。
- **Redis 里尚未异步持久化的已读位置。** MySQL 水位更低，重建后未读偏多；不会出现假已读。
- **群消息发送者昵称快照。** 用当前昵称重建，可能与发送时不同。
- **超过 7 天的去重记录。** 本来已过期。
- **RabbitMQ 自身的数据。** 不在本版范围；若 RabbitMQ 也丢失，其中的消息无法恢复。

## 重建命令

`im-server -rebuild-redis`，由 `imctl rebuild-redis`（验证实例 `imctl --verify rebuild-redis`）调用。与 `backfill-seq` 一样是独立的一次性命令，不依赖后端运行。

### 前置条件与互斥

- 后端已停止，端口无监听，没有同名进程。
- 持有 Redis 的 `rebuild:lock`（30 分钟 TTL，带 token 释放）。存在 `rebuild:lock` 或 `backfill:lock` 时后端拒绝启动；两个命令互斥。
- MySQL 中两张消息表都不存在 `seq` 为空的行。存在说明还没完成旧数据回填，提示先执行 `backfill-seq`。
- 队列排空失败、Redis 或 MySQL 不可用时中止，不写 `seq:ready`。

### 执行顺序

1. **排空队列。** 消费 `messages.persist` 和 `group.messages.persist` 到空，手动确认；毒消息按 v1.8.2 的规则进死信并计入报告。超时（初始 10 分钟）仍未排空则中止。
2. **清理本命名空间。** 只删除已知前缀的键（消息实体、索引、feed、conv-last、计数器、去重、已读、群投影、Stream、`index:epoch`、`seq:ready`），分批 `DEL`。不使用 `FLUSHDB`/`FLUSHALL`，不删除锁和未知键。
3. **全局计数器。** 设为 `GREATEST(MAX(server_message_id)（两张表）, message_id_sequences.last_message_id)`，保证新消息号不重复。
4. **消息主遍。** 按自增主键分批（默认 1000 行，pipeline 写入）遍历 `messages`：写实体、`dm:pair`（分数 `seq`）、收发双方的 `dm:feed`（分数全局号）、双方的 `dm:conv-last`、会话计数器，并写 7 天内的去重记录和剩余 TTL。群消息按同样方式写 `group-messages`、`group:{G}:inbox`、`group:{G}:seq`；发送者昵称用当前用户资料。
5. **私聊已读水位。** 分批读 `conversation_reads`，`HSET dm:read:{user} peer last_read_seq`。群水位由启动时的重建负责，命令不重复写。
6. **`index:epoch`。** 全量建立 feed 后设为 0；feed 从第一条消息起完整。
7. **校验。** 每个会话 `Redis ZCARD = MySQL COUNT = MAX(seq) = 计数器`；每个用户 `dm:feed` 条数等于 MySQL 参与消息数；水位不大于计数器；抽样读回消息实体，正文、`seq`、收发双方与 MySQL 一致；去重记录数与 7 天内消息数一致。
8. **写入 `seq:ready`。** 校验全部通过后才写，随后释放锁并输出统计（会话数、消息数、去重数、耗时、队列排空数）。

### 幂等与失败

- 重复执行结果一致：先清理再重建；同一份数据两次重建的计数指纹相同。
- 中途失败不写 `seq:ready`，后端继续拒绝启动；修正后重跑。
- 锁未释放（进程被杀）最多阻塞 30 分钟，可用 token 模式确认后删除。

## 定时一致性检查

在 v1.8.2 的对账循环里增加反方向检查，与现有“补 MySQL”共用同一趟 MySQL 统计扫描，不额外全表查询。

### 每 5 分钟

1. **会话条数与计数器。** 每页 MySQL 的 `COUNT(*)`、`MAX(seq)` 与 Redis 的 `ZCARD(dm:pair)`/`ZCARD(group:{G}:inbox)`、会话计数器比较。
   - Redis 计数器小于 MySQL `MAX(seq)`：用只增不减的 Lua 抬到 MySQL 值，避免新消息撞号。
   - Redis 索引条数少于 MySQL 条数，或计数器小于 `MAX(seq)`：判定为 Redis 缺数据，进入补写。
   - 现有方向（Redis 多于 MySQL）仍按 v1.8.2 补 MySQL；两个方向在同一趟里互不影响。
2. **私聊水位。** 分批比较 `conversation_reads.last_read_seq` 与 `dm:read`。Redis 更旧时抬到 MySQL 值（安全方向：未读偏多，不会假已读）。Redis 更新是正常现象（异步持久化还在路上），不动。
3. **群水位。** 同样比较 `group_members.last_read_seq` 与 `group:{G}:read`，只抬高。

### 每小时

1. **消息实体抽样。** 每个会话取最老、最新各 2 条，再按轮换游标抽取一部分，读回 Redis 实体与 MySQL 比较。用于发现“索引在、正文没了”。
2. **feed 抽样。** 按轮换游标取 50 个用户，比较 `ZCARD(dm:feed)` 与 MySQL 中该用户参与的消息数。
3. **`dm:conv-last` 抽样。** 每个抽样用户比较会话预览与 MySQL 最新一条。

### 自动补 Redis 的上限

- 每轮最多补 200 条消息，单个会话最多 50 条，按 `seq` 升序。
- 单个会话缺失超过 200 条，或缺失比例超过 20% 且超过 20 条，标记 `needs_rebuild`，不再自动补，只写日志并在 `/ops/infra` 告警。
- 补写只增加数据，不删除、不覆盖已有实体；会话计数器只升不降；不改 MySQL。
- 补写失败的条目留在下一轮重试，同一（会话，`seq`）每小时最多记一条错误日志。

### `/ops/infra`

`pipeline.reconcile` 增加：`redis_missing`、`redis_repaired`、`watermarks_raised`、`feed_repairs`、`needs_rebuild`、`last_deep_audit_at`、`deep_audit_error`。

## 失败与降级

| 场景 | 行为 |
| --- | --- |
| Redis 整体丢失（`seq:ready` 也没了） | 监视器关闸，接纳和未读返回 503；历史回落 MySQL；人工执行重建后恢复 |
| 只丢部分键（`seq:ready` 还在） | 5 分钟检查发现并小量补回；超出上限时告警，建议重建 |
| 重建时后端仍在运行 | 命令拒绝执行 |
| 持久化队列在超时内未排空 | 中止重建，不写 `seq:ready`，报告剩余条数 |
| 重建中途失败 | 不写 `seq:ready`；清理后重跑 |
| 队列里的毒消息 | 进入死信，继续排空；报告中列出条数 |
| MySQL 缺 `seq` 的历史行 | 拒绝重建，提示先执行 `backfill-seq` |

## 验收方向

1. 停机后清空验证命名空间（模拟整体丢失），执行 `imctl --verify rebuild-redis`，启动后端：登录、历史、未读、会话列表、私聊增量同步、重发去重全部正确。
2. 重建前后 MySQL 数据不变；重建后每个会话 `ZCARD = COUNT = MAX(seq) = 计数器`。
3. 在 RabbitMQ 中预留未落库消息，重建命令先排空再重建，这些消息在重建结果中；不排空直接重建会被拒绝或产生撞号，验证不会发生。
4. 后端运行时执行重建被拒绝；`rebuild:lock` 存在时后端拒绝启动。
5. 同一份数据连续重建两次，统计指纹一致。
6. 运行期删除少量实体、索引成员和一条水位：5 分钟内自动补回，`/ops/infra` 显示修复数。
7. 删除某个会话大部分消息：超过上限后只告警 `needs_rebuild`，不再继续补。
8. 私聊/群水位方向：MySQL 更旧时不动，Redis 更旧时抬高到 MySQL。
9. v1.8.1/v1.8.2 行为不变：`seq` 连续、未读、死信、对账、监控。

## 不在本版范围

- RabbitMQ 自身丢失后的恢复；
- 跨实例和分布式；
- Redis 键容量、TTL 治理和性能调优（v1.9）；
- 超过 7 天的去重记录重建；
- 未持久化已读事件的恢复（只能接受未读偏多）。

## 风险

1. **重建耗时长。** 消息越多越久，期间后端不可用。分批 + 进度日志，验证时记录实际耗时。
2. **重建写错会放大问题。** 校验覆盖条数、编号、水位、实体抽样和 feed 计数，任何一项失败都不写 `seq:ready`。
3. **定时检查增加 Redis 负担。** 每 5 分钟只有 `GET` 和 `ZCARD`，与现有对账共用 MySQL 扫描；实体和 feed 抽样放在每小时并限量。
4. **自动补与并发接纳同时发生。** 补写只增加数据、计数器只升不降，重复写由 ZSET/HASH 幂等吸收；需要并发测试。
5. **群昵称快照与历史不一致。** 只影响显示，写入文档。
6. **部分丢失可能落在两次检查之间。** 最长 5 分钟的未读偏差，历史仍正确。

## 实施小步

1. **store：** 分批遍历消息和群消息、参与消息计数、按会话列举实体、已读状态读取（复用现有查询）。
2. **messaging：** 抽出的“把一条消息写入 Redis”投影函数（重建和自动补共用）；`RedisRebuilder`（清理、主遍、水位、epoch、校验、写 ready）；`rebuild:lock` 与启动门禁。
3. **messaging：** 对账增加反方向检查、水位抬高、自动补上限、每小时抽样和新状态字段。
4. **cmd 与 imctl：** `-rebuild-redis`、`rebuild-redis` 子命令、`--verify` 支持、停机守卫、批量参数。
5. **脚本与文档：** 运维文档补充重建步骤、锁清理、验收记录；`imctl_test.sh` 覆盖新子命令。
6. **验证：** 单元测试、`go vet`、`-race`、独立对抗审查、8199 隔离演练（含模拟整体丢失和部分丢失），清理测试数据。
